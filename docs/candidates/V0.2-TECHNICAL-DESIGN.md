## A. CURRENT CONTRACT

Established by reading `umbral/src/`, not by memory. v0.1 is the state being changed.

**Observation, per run.** `scan::scan` walks the root (`walkdir`, `follow_links(false)`,
`min_depth(1)`) and calls `symlink_metadata` on every entry. Each `Entry` carries
`path`, `kind`, `dev`, `ino`, `size`, `mtime`. Errors are collected, never dropped, and
`Scan::complete()` is `errors.is_empty()`.

**Content, per regular file.** `content::observe_content` runs `stat` → read (64 KiB
streaming, BLAKE3) → `stat`, comparing `dev`+`ino`, size and nanosecond `mtime`. On a
detected change it retries once; still changing → `Stability::Unstable` with no hash.
`ContentObservation::valid_hash()` is the single gate: a hash exists only for a `Stable`
read.

**Persistence.** `log::ObservationLog` (trait) with one implementation, `SqliteLog`.
Schema `umbral-v0.1`: tables `schema_meta`, `run`, `observation`. Columns include `dev`,
`ino`, `size`, `mtime_s`, `mtime_ns`, `hash`, `hashed_len`, `hash_stability`,
`hash_deltas`, `obs_error`. A `CHECK` forbids a stored hash without a stability verdict.
*(Note added 2026-10-02: this describes the baseline the design was written against. Since
`D-V01-10`, corrected under `UD-029`, the v0.1 log schema is `umbral-v0.1.1`, which adds
`content_error`; a `umbral-v0.1` log is migrated additively. This changes no analysis below
and selects no v0.2 persistence schema.)*
No projection table, no derived column — `entries`, `errors` and `complete` are computed on
read. `open_read_only` opens with `SQLITE_OPEN_READ_ONLY`, which is what makes the
read-only commands genuinely read-only.

**Classification.** `reconcile::reconcile` is pure — no syscalls, no clock, no database —
and consumes two `ObservationSet`s. Five phases: (1) same path + same `dev`+`ino` →
`Unchanged`/`Modified`, decided by size+mtime and refined by hash equality; (2) leftover
`dev`+`ino` matched globally → `RenamedOrMoved`, or `Ambiguous(ConflictingCandidates)` when
more than one candidate exists on either side; (3) same path without shared identity →
`Recreated` (hashes differ) or `Ambiguous` (hashes equal → `DuplicateContentNotIdentity`;
no evidence → `NoContentEvidence`); (4) new paths → `Created`; (5) vanished paths →
`Deleted` only when the current scan is complete, else `Unobserved`.

**The four labels.** `observed` is reserved by `F-V01-2` for what the filesystem itself
states per entry — enforced by the `OBSERVED_FIELDS` allowlist (`canonical=`, `kind=`,
`size=`, `mtime=`) and `DERIVED_ONLY_FIELDS`, with `label_contract_violations` as the check.
Everything the tool computes is `derived`. `ambiguous` and `unknown` are separate labels.
`BANNED_LEXICON` forbids anthropomorphic vocabulary in rendered output, enforced by
`no_command_output_uses_banned_vocabulary`.

**What v0.1 does NOT do.** `observe` re-reads and re-hashes every regular file on every
run, unconditionally. There is no consultation of the previous run at all: `main::observe`
scans, hashes every file, and appends a run. That is known limitation 1 (`O(corpus) per
run`), and it is the thing v0.2 attacks.

## B. THE TECHNICAL PROBLEM

### B.1 What "incremental" means here, precisely

"Incremental" is a claim about **which work grows with what**. Stated as a cost model, one
`observe` run over a corpus of `|C|` entries with `k` entries whose evidence is
insufficient:

| # | Work | Complexity | Optimisable by v0.2? |
|---|---|---|---|
| 1 | Traversal and `stat` of every entry | `O(\|C\|)` | **No.** `UD-016` forbids claiming it |
| 2 | Loading the previous run's observations | `O(\|C\|)` rows | **No** — and it is a **new** cost v0.2 introduces |
| 3 | Reading and hashing content | `O(k)` bytes | **Yes.** This is the whole claim |
| 4 | Persisting one row per entry per run | `O(\|C\|)` rows | **No** |
| 5 | Reconciliation (`changes` only, not `observe`) | `O(\|C\|)` | **No** |

So the honest statement is: **v0.2 reduces item 3 from `O(|C|)` to `O(k)`. Items 1, 2, 4
and 5 stay `O(|C|)`.** Item 2 is worth naming explicitly because it is easy to overlook:
the skip decision cannot be made without knowing what was known, so a re-observation must
read the previous run's rows. v0.2 therefore trades one `O(|C|)` cost for another and
removes a third.

### B.2 The measurement does not support a stronger claim, and is itself unreliable

`UD-016`'s evidence and `V0.2-SCOPE-PROPOSAL.md` §2 both quote a baseline. Re-measured
2026-09-13 with `cargo run --release --example bench`, five consecutive runs, tmpfs, same
corpus (2000 files × 4 KiB in 40 directories):

| Metric | Recorded (v0.1 §EVIDENCE) | Run 1 | Run 2 | Run 3 | Run 4 | Run 5 |
|---|---|---|---|---|---|---|
| cold scan (stat only) | 23.9 ms | 8.6 | 9.4 | 7.8 | 8.8 | 8.0 |
| hash all files | 102.5 ms | 29.8 | 54.9 | 29.5 | 31.3 | 32.0 |
| full observation, twice | 209.6 ms | 74.9 | 137.4 | 84.9 | 79.0 | 76.7 |

Two findings, both relevant to the design:

**F-TD-1 — the recorded figures are not reproducible.** Every figure is roughly 2×–3.5×
today's, and the spread *within* one session is already 1.8× (hash: 29.8 → 54.9 ms). The
recorded run's conditions were not stated: no repeat count, no statement of system load, no
statement of whether the numbers are a single observation. They are not wrong; they are
**one observation presented as a baseline**. The recorded hash throughput (76.2 MiB/s)
against today's (267.8 MiB/s) suggests the earlier session ran under load.

**F-TD-2 — the decomposition in `V0.2-SCOPE-PROPOSAL.md` §2 is arithmetically unsound.**
That table presents `scan 23.9 ms` and `content read + hash 102.5 ms` as components of
`full observation 209.6 ms`, and derives a third component, `remainder (persistence,
assembly) ~83 ms (40%)`, by subtraction. But the source metric in `v0.1.md` §EVIDENCE is
labelled **"full observation (scan + hash), twice"** — it measures *two* `observe_set`
calls, while `scan` and `hash all files` are *one-call* figures. Comparing a two-call total
against one-call components is what produces the "remainder": 209.6 − (23.9 + 102.5) = 83.2.
**That remainder was never measured and does not correspond to any work.** Today's
measurement confirms the structure: `full observation, twice` ≈ 2 × (scan + hash), with no
material remainder (run 1: 74.9 total ≈ 2 × 37.5; scan 8.6 + hash 29.8 = 38.4).

Consequences, stated because they change how the design must be justified:

- The optimisable share is **not** 49%. Taking the recorded one-call figures, scan is
  23.9 / 126.4 = 19% and read+hash is 81% of a per-run observation. The proposal
  understated the case it was arguing.
- The corrected arithmetic **strengthens** `UD-016`'s decision (scope the objective to
  read/hash) — the share is larger, not smaller. `UD-016`'s own text does not contain the
  decomposition and needs no correction; only the proposal's §2 table does.
- **No design decision in this document rests on any of these numbers.** They are unstable
  at the 2× level between consecutive runs on one machine. The instrument for the objective
  is the counter (§G, P10), exactly as `V0.2-SCOPE-PROPOSAL.md` §11 already requires.

### B.3 The problem the design must actually solve

Not "make it faster". Two things, and the second is the hard one:

1. **Skip work that does not need doing**, without weakening any existing guarantee.
2. **Preserve verdicts, evidence, ambiguity and reconstruction** while doing so — and be
   able to say, in the output, which results came from reading bytes and which did not
   (`UD-017`), with applicability that is determinable (`UD-019`).

The tension is structural: any skip is a decision made from metadata, and metadata is not
content. `UD-017` does not forbid skipping; it forbids presenting a skip as a verification.
The design therefore has to make the distinction **structural** rather than a matter of
wording.

## C. RE-OBSERVATION MODEL

### C.1 The decision, as a pure function

The skip decision must be a **pure function** over (previous observation, current entry),
for the same reason `reconcile` is pure: so it can be tested against hand-built observation
sets and never depends on what a filesystem happens to do (the F-6 discipline,
`V0.2-SCOPE-PROPOSAL.md` §11).

```
decide(previous: Option<&Observation>, current: &Entry) -> Decision

Decision::Skip { verified_in_run }      // reuse a prior verified reading
Decision::Read                          // read and hash now
```

The condition, stated as the design proposes it:

```
Skip(previous, current) requires ALL of:
  1. previous exists and previous.kind == File and current.kind == File
  2. previous.hash is present AND previous.stability == Stable
        -- a skip must rest on a reading that actually happened
  3. previous.dev == current.dev AND previous.ino == current.ino
  4. previous.size == current.size
  5. previous.mtime == current.mtime
  6. [if ctime is adopted, D-PEND-2] previous.ctime == current.ctime
otherwise -> Read
```

Condition 2 is the one that is easy to get wrong and is load-bearing: **a skip requires a
verified baseline.** If the previous observation recorded `Unstable`, an error, or no hash,
there is nothing to reuse and the entry is read. Without condition 2, an unverified state
would propagate forward across runs and acquire the appearance of verification — precisely
the failure `UD-017` exists to prevent.

### C.2 Carrying the reading forward, and why it is necessary

A skipped entry records **no new reading**. The question is whether the observation carries
the previous hash forward.

**It must, or verdicts change.** Worked example with `hash` *not* carried:

- Run 1: file `f` is read, hash `H1`.
- Run 2: metadata unchanged → skipped → no hash recorded for run 2.
- Run 3: `f` is `touch`ed (mtime moves, bytes identical) → condition 5 fails → read → `H2 == H1`.
- `changes` compares runs 2 and 3. `same_observable` is false (mtime differs);
  `hashes_equal(prev, cur)` is **false**, because run 2 recorded no hash. Verdict:
  `Modified`.

v0.1 on the same sequence gives `Unchanged` with `content-changed=false`, because run 2
read the bytes and its hash equals run 3's. **The verdict differs, and the objective
forbids that.**

With the hash carried forward, `hashes_equal` compares `H1` against `H2` and returns
`Unchanged`, matching v0.1.

### C.3 The invariant that carrying forward would break, and how it is kept

`umbral/src/log/mod.rs` states: *"A persisted hash represents exactly the bytes Umbral read
during one valid observation."* Carrying a hash into a run that did not read it would make
that sentence false.

The design keeps it true by naming the run that read the bytes:

```
observation.hash             the bytes' digest (as today)
observation.hash_stability   the stability verdict of that read (as today)
observation.hash_read_run    NEW: the run in which those bytes were read
```

- A fresh read sets `hash_read_run = this run`.
- A skip copies `hash` and `hash_stability` from the previous observation and copies
  `hash_read_run` **unchanged** — it names the run that actually read them.

Then the two predicates that the whole contract turns on become structural, not verbal:

```
content-verified in run N   <=>   hash_read_run == N
basis = metadata-match      <=>   hash present AND hash_read_run < N
basis = unavailable         <=>   no valid hash, or an error
```

This is what makes `UD-017`'s mandatory rule enforceable by a test rather than by review:
"content-verified" is a comparison of two integers, and a skipped entry cannot satisfy it.

**This is a REQUIREMENT, not a design preference** (`UD-021`). Where v0.2 reuses a content result
without re-reading bytes, the reconstruction **must** be able to distinguish that result from a
new content verification. The evidence needed to distinguish at least three states must be
persisted:

| State | Meaning | Distinguishing evidence |
|---|---|---|
| content was actually read and verified | the bytes were read in this run | the reading's run identity equals this run |
| prior evidence reused through metadata | the bytes were **not** read in this run | the reading's run identity is earlier than this run |
| UNKNOWN / error | no valid reading, or an error | absence of a valid reading, plus the error state |

**The concrete persistence schema is NOT decided here.** `hash_read_run` is a name for the
distinguishing evidence, not a settled column definition — the column set, its type, whether the
attribution is a run id or something else, and the migration for v0.1 logs are all open (§J).
What is fixed is the **distinguishability**: no persisted form is acceptable if it cannot tell
these three apart. Naming one candidate column must not be read as having designed the schema.

### C.4 What happens in each case

Stated for every case the mandate names. `Skip` below always means the full condition of
§C.1 including condition 2.

| Case | Decision | Verdict | Notes |
|---|---|---|---|
| **Created** | `Read` | `Created` | No previous observation for the path; nothing to reuse |
| **Deleted** | — (nothing to read) | `Deleted` / `Unobserved` | Unchanged from v0.1; `Deleted` only when the scan is complete |
| **Modified (metadata moved)** | `Read` | `Modified` | Condition 4 or 5 fails. This is how a real content change is detected |
| **Unchanged (metadata equal)** | `Skip` | `Unchanged` | `basis=metadata-match` |
| **Rename / move** | `Skip` | `RenamedOrMoved` | Phase 2 matches on `dev`+`ino`; the carried hash travels with the object, so the new path is not permanently degraded to "never verified" |
| **Atomic replacement** | `Read` | `Recreated` (or `Modified`) | `ino` differs → condition 3 fails. **v0.1 behaves identically**; this is the case where trusting size+mtime alone would be wrong, and the condition does not trust them alone |
| **Inode reuse** | `Skip` **if** the metadata matches | **`Unchanged` — WRONG** | See §C.5. This is the one case where the metadata-only condition can produce a false skip |
| **Hard links** | Per path, independently | Two entries, one object | A content change through either path moves the inode's metadata, so both fail the condition and both are read. Consistent |
| **Symlinks** | No content decision | `Symlink` entry | Never resolved to a target's content (`symlink_metadata`), so no skip applies |
| **Insufficient permissions** | `Read`, which fails | `basis=unavailable` | The read attempt yields `PermissionDenied`; no hash; no skip next run (condition 2 fails). Cost: a failed `open`, which reads 0 bytes |
| **File mutated during read** | `Read`, guard fires | `Unstable`, no hash | Unchanged from v0.1. Next run: condition 2 fails → read again. Conservative and self-correcting |
| **Incomplete observation** | `Read` for that path | `Unobserved` | A path with an error has no previous observation to reuse. And a run that is incomplete still cannot produce `Deleted` |
| **Error on a previously-verified path** | `Read`, which fails | `basis=unavailable` | The prior reading is **not** reused: current metadata could not be obtained, so the condition cannot be evaluated. Absence of evidence is not evidence |

### C.5 The false skip that cannot be removed by metadata

**Inode reuse with matching metadata.** If a file is deleted and a new one is created at
the same path, and the filesystem hands back the same `dev`+`ino` (v0.1 records that this
did happen on the ext4 CI runner), and the new file happens to have the same size and mtime
— then conditions 1–5 all hold, the skip fires, and the tool reports `Unchanged` for a file
whose content is different.

**No metadata-only condition can close this**, because the condition *is* metadata. Two
things can:

- **`ctime`** (condition 6, if adopted): `ctime` is not settable from userland (§D), so a
  delete-and-recreate at the same inode moves it. The EXP-CTIME probe measured this on
  tmpfs and btrfs.
- **Reading**, which is what is being avoided.

This is stated as a **known limitation of any metadata-based skip**, and it is why §D is
not a formality: it decides whether this false skip is reachable by an ordinary process.

### C.6 What the model does not claim

- **It does not claim that a content change is always detected.** A writer that restores size
  **and** mtime (and `ctime`, if adopted) between runs, with the inode unchanged, is invisible
  to the skip condition. This is `R2` in `V0.2-SCOPE-PROPOSAL.md` §7, moved from inside one
  read to between two runs.

  **F-TD-3 — correcting this document's own first draft.** The first version of this section
  claimed that v0.1 detects this case "because it always reads", implying a verdict
  divergence. **That was wrong, and re-reading `reconcile` showed it.** Phase 1 evaluates
  `same_observable` *first*:

  ```
  if same_observable(prev, cur)      -> Unchanged        // size + mtime equal
  else if hashes_equal(prev, cur)    -> Unchanged        // metadata moved, bytes did not
  else                               -> Modified
  ```

  With size and mtime equal, `same_observable` is true and **v0.1 also reports `Unchanged`**,
  without consulting hashes at all. The hash comparison is a refinement for the case where
  metadata *moved* — it exists to avoid a false `Modified`, not to catch a false `Unchanged`.

  So the divergence is **not in the verdict**. It is in the **evidence**:

  | | `changes` verdict | what the log records | what a reader of `show` can see |
  |---|---|---|---|
  | **v0.1** | `Unchanged` | run N-1 hash `H1`; run N hash `H2` | that the bytes differ across runs |
  | **v0.2 with skip** | `Unchanged` | `H1` carried forward; `hash_read_run` still names the earlier run | nothing — the change left no trace |

  This makes the risk **sharper, not milder**: it is not a wrong verdict a test would catch,
  it is a silent loss of recorded evidence in a system whose whole claim is reconstruction.
  It is why `hash_read_run` must be persisted (§C.3) — with the run attribution, a reader can
  at least see *that the reading is old*, even when it cannot see that the bytes moved.

  This correction is recorded rather than quietly fixed because the same mistake — assuming
  that always-reading must imply a different verdict — is available to whoever designs the
  tests. `P5` in §G was already reformulated for the same reason; `P14`'s enumerated cases and
  `E-TD-2`'s falsifier are stated in terms of **recorded evidence**, not verdicts.

- **It does not claim the run is `O(changes)`.** Only item 3 of §B.1 is.
- **It does not claim a change that happens and is reversed between two runs is visible.** That
  is inherent to sampling, not to this design.
- **It does not claim the `ctime` residual is closed.** `ctime` is **not adopted** (§D.9), so
  the false skip of §C.5 is **reachable** in the design as it stands. That is a known
  limitation, and it is stated as one — not as a guarantee, and not as a property that passes.

## D. ctime ANALYSIS — STATUS OF D-PEND-2

`D-PEND-2` (does `ctime` enter the skip condition?) is **OPEN**, and this document does not
close it. It narrows what the answer must be, and it states what is still missing.

### D.1 What ctime is, in the target environment

The inode change time: stamped by the kernel whenever the inode's metadata changes. On
Unix it is exposed by `stat`/`lstat` as `st_ctime` + `st_ctime_nsec`, which Rust surfaces
as `MetadataExt::ctime()` / `ctime_nsec()`. It is **not settable from userland**:
`utimensat` sets atime and mtime, not ctime.

### D.2 What may and may not be inferred

**May be inferred:** that something about the inode changed since the timestamp. `ctime`
moving is evidence *of inode-level change*. It is not evidence about bytes.

**May not be inferred:** that the content is unchanged because `ctime` is equal. `ctime`
equal is *absence of a change signal*, which is not *evidence of no change* — the same
distinction `UD-017` draws for `metadata sufficient`. This is the trap
`V0.2-SCOPE-PROPOSAL.md` §6 names, and it is the reason `UD-018` forbids `ctime` from
supporting a `content-verified` claim.

### D.3 Can it serve as sufficient evidence to avoid reading?

**Yes for the purpose the design needs, and no for the purpose it must never serve.** The
distinction is the whole of `UD-018`:

- As a **condition in the skip predicate**: legitimate. It can only make the predicate
  stricter, because it is an additional equality that must hold.
- As a **claim about content**: forbidden, always.

### D.4 When it can produce a false "stable"

Enumerated, because a false `stable` is the failure mode that matters:

1. **A filesystem that does not generate its own timestamps** — network filesystems, some
   FUSE mounts, or a mount that mirrors timestamps from a server. Not measured here.
2. **Coarse timestamp granularity.** The kernel documentation
   (`research/sources/S12-KERNEL-MULTIGRAIN-TIMESTAMPS.md`) records that a change inside one
   jiffy can end up with the same timestamp, and that multigrain timestamps — which reduce
   this — are a **per-filesystem opt-in** (`FS_MGTIME`). On a filesystem that has not opted
   in, a write within the same tick as the previous `ctime` may leave it equal.
3. **A clock that moves backwards or is adjusted**, which the kernel documentation notes.
4. **ext4 — UNKNOWN.** The only ext4 environment available to this project is the CI
   runner. The EXP-CTIME probe does not run there.

Cases 1–3 are **not reachable by an ordinary userland process writing to a local
filesystem**, which is the case the tool is designed for. They are reachable by the
environment, which is why they must be declared rather than dismissed.

### D.5 Does it need to be combined with other metadata?

**Yes — `ctime` is only meaningful as an addition.** Alone it says "the inode changed
sometime", which cannot distinguish a change since the last run from one before it. It is
the conjunction with `dev`+`ino`+size+mtime that makes it a *skip* condition, and the
conjunction is what makes it safe: it is strictly stronger than the current metadata set.

### D.6 Does the conclusion depend on filesystem and kernel?

**Yes, and asymmetrically.** The *safe* direction is portable: `ctime` moving is evidence of
change on any filesystem that generates timestamps, so including it can only cause extra
re-reads. The *unsafe* direction — `ctime` equal implying unchanged — is not portable, and
on a filesystem that mirrors or coarsens timestamps it is simply false.

### D.7 Stated as a verifiable property, not as intuition

> **P-D2.** For every case where the skip condition of §C.1 without `ctime` would fire and the
> file's bytes differ from those named by `previous.hash`, adding the `ctime` equality
> causes the condition **not** to fire.
>
> - **Falsifier:** a case where content differs, size and mtime are equal, `dev`+`ino` are
>   equal, and `ctime` is *also* equal. The EXP-CTIME probe's case 1 searches for exactly
>   this and did not find it on tmpfs or btrfs.
> - **Not falsifiable here:** on ext4, and on filesystems that do not generate their own
>   timestamps. Declared `UNKNOWN`.

> **P-D2b (monotonicity).** Adding `ctime` to the condition can only reduce the set of
> skipped entries, never enlarge it.
>
> - **Falsifier:** any input where the condition with `ctime` fires and the condition
>   without it does not. This is checkable exhaustively over hand-built observation sets,
>   because both conditions are pure functions — no filesystem required.

### D.8 The four categories, kept apart

The mandate requires these to be separated, and they were being blurred by the first draft's
recommendation. Nothing below is a decision.

**DEMONSTRATED (properties the evidence supports):**

| # | Property | Evidence | Scope of the evidence |
|---|---|---|---|
| D-A | A writer that restores size and exact mtime still moves `ctime` | EXP-CTIME case 1 | tmpfs, btrfs; **not** ext4 |
| D-B | `ctime` is not settable from userland (`utimensat` cannot forge it) | EXP-CTIME case 6; kernel documentation | Unix; general |
| D-C | Adding a term to the skip condition can only reduce the skipped set | Pure logic; checkable without a filesystem | General — P-D2b |
| D-D | A backdated mtime coexists with a current `ctime` | EXP-CTIME case 7 | tmpfs, btrfs |

**UNKNOWN (not established by any evidence this project holds):**

| # | Question | Why it is unknown |
|---|---|---|
| D-E | Whether `ctime` changes on **ext4** under the same probe | No local ext4; the probe does not run in CI |
| D-F | Whether `ctime` moves on a filesystem that does not generate its own timestamps | Asserted from documentation; never measured |
| D-G | Whether a change within one clock tick can leave `ctime` equal | Kernel documentation says it can; not reproduced here |
| D-H | Whether `ctime` behaviour is stable across kernels and filesystems | One probe, one kernel, one session |

**TECHNICAL RECOMMENDATION (a proposal, explicitly not adopted):**

> Include `ctime` in the skip condition as an `Option` equality, with the skip **disabled**
> for an entry where `ctime` cannot be obtained.

Rationale: it is the only candidate that narrows §C.5's false skip without a read; it moves the
condition in the safe direction only (D-C); and the residual is confined to environments the
tool does not target, where it must be declared rather than hidden.

**DECISION: none. `ctime` is NOT adopted.** `D-PEND-2` remains **OPEN**. The design as it
stands uses the condition of §C.1 **without** condition 6, which means:

- the false skip of §C.5 (inode reuse with matching metadata) is **reachable**;
- this is recorded as a **known limitation**, not as a guarantee and not as a passing property;
- `ctime` stays a **candidate technical hypothesis**, neither adopted nor eliminated.

### D.9 What D-PEND-2 still lacks

The evidence is **one probe, run once, on two filesystems, written after the fact** (the
EXP-CTIME record states this provenance honestly). Missing before the question can be answered
on evidence:

1. **ext4.** Only CI can measure it, and no CI job runs the probe. → `E-TD-3`.
2. **A pre-specified probe.** The existing one was specified after running, with the case list
   chosen by the reasoning that wanted `ctime` to work. That is recorded, and it is **not**
   repaired by re-running the same script, nor by presenting a new run as new evidence for the
   old question. → `E-TD-2`, pre-registered in §H.
3. **A filesystem that does not generate its own timestamps** — the residual failure mode in
   §D.4 case 1 is asserted from documentation, never measured.
4. **The condition expressed as a pure function and falsified exhaustively** (P-D2b), which
   does not need a filesystem at all and has not been written.

**D-PEND-2 remains OPEN.** Reaching a decision requires `E-TD-2` and `E-TD-3` to have been
executed and recorded; neither has been executed.

## E. basis TRACEABILITY — APPLICABILITY AND PROVENANCE

`UD-019` requires that the relation between a `basis` and what it applies to is
determinable under the contract, and deliberately does not select a representation. The
three permitted families are compared below. **Family A is not selected by default.**

### E.1 What the evidence actually shows

Measured over `experiments/exp-ai-01/material.txt` — every rendered line, checked for a
field naming a subject (`run=`, `last-run=`, `path=`, `old-path=`, `from-run=`, `to-run=`,
`root=`, `canonical=`, `workspace-id=`, `state-dir=`):

```
27 rendered lines.  16 derived lines carry NO subject field.
```

They fall into exactly two classes, and the distinction is the finding:

- **Class 1 — aggregate/summary lines.** `count unchanged=4` (×8), `entries=6 files=5 …`,
  `content-verified=5`, `log-runs=1 …`, `initialised=true`. Their subject is the command's
  overall scope — the workspace for `status`, the comparison for `changes` — and it is
  established by a preceding header line (`compared from-run=1 to-run=2 complete=true`).
- **Class 2 — one line, and it is the one that failed.** `path-encoding=escaped
  reason=path-is-not-valid-utf8` (material line 65). It is not an aggregate — it is about a
  *specific rendering of a specific value*. It is not a detail line — it names no path. It
  sits between the two classes and belongs to neither.

That is the precise diagnosis of the EXP-AI-01 divergence: **the output already has a
subject convention, and this line is the single place where a value with a specific subject
was emitted without naming it.** Note also that `path-encoding=` is not the field `path=`;
the prefix makes it *look* scoped while carrying no subject.

Additionally, verified: `show`'s `observed kind=file size=10 mtime=…` line carries neither
a path nor a run — the least-scoped line in the corpus. Its subject is only the command
argument (CTF-2).

### E.2 The comparison

Evaluated against the criteria the mandate fixes. **No family is assumed correct, and the
per-line form is not presumed sufficient because it is simple.**

| Criterion | **A. Explicit field** | **B1. Declared convention, per-line** | **B2. Declared convention, scope-by-position** | **C. Other representation** |
|---|---|---|---|---|
| Determinability | Direct: the subject is on the line | Determinable *if the contract states the rule*; the rule must then be enforced | Determinable only while nothing reorders | Depends on the representation |
| Robust to **reordering** | Total | **Total** — association is intra-line | **Fails** — the association *is* the order | Depends; an explicit id survives |
| **Automatic parsing** | Easy, but the field must be added to every emitting site | Easy: one field per line, no state machine | Requires a parser that tracks the last scope header — fragile | Depends |
| **Consumption by AI** | Best in principle: zero inference | Good **once the contract is stated**; today it is neither stated nor enforced, which is exactly what failed | Bad: requires positional inference, which is what EXP-AI-01 showed is not reliable | Unknown |
| **Multiple entries** | Each line carries its own | Per-line: yes | Yes, one scope per group — but a malformed group silently mis-scopes | Depends |
| **Serialization / deserialization** | Survives round-trip if the field survives | Survives round-trip **only at logical-line granularity**: if lines are wrapped or re-flowed, an intra-line association can be split. The logical line is the unit, and the contract must say so | Survives round-trip only if order is preserved and the reader replays the scope stack | Best if the representation is structured; worst if it invents vocabulary |
| **Format evolution** | Adding a second subject-naming field alongside `path=` creates two sources that can disagree | Extends what exists; a **flat** field does not scale to a multi-valued provenance (`UD-017` asks for the evidence the result rests on, which is a set) | Same as B1, plus the positional dependency | Depends |
| **Human consumption** | Verbose: the subject repeated on every line | Terse; matches the existing shape | Terse | Unknown |
| **Compatibility with current output** | Adds a field to lines that already carry `path=` → **duplication** | 26 of 27 material lines already conform | Same, but relies on the one line that failed | Diverges |
| **Ease of test** | Easy | Easy, once the rule is formal | Hard | Harder |
| **Ambiguity risk** | Low | Low **if enforced**; unbounded if only documented | **High** — accidental ambiguity of presentation, which the mandate forbids relying on | High — undefined vocabulary |

**The criterion the mandate makes obligatory:** applicability must be determinable and
verifiable, *without depending on an accidental ambiguity of presentation*. That criterion
**eliminates B2 outright** — scope-by-position is precisely an association that survives only
by accident of presentation. It also sets the bar B1 must clear: B1 is only acceptable if the
rule is **stated in the contract and enforced by a test**, not merely true of today's output.

### E.3 Assessment — and a gap none of the families closes by itself

**Family A is the strongest on determinability and the weakest on fit.** Every line that will
carry `basis` in `changes` already carries `path=` — the subject is present. Adding `subject=`
beside it names the same thing twice, and if the subject is a path it must be escaped, which
duplicates the escape contract's surface and creates a second place for the two renderings to
disagree. A is not more determinate where the subject already exists; it is only more verbose.

**Family C adds vocabulary, which `UD-019` explicitly constrains.** A stable per-entry
identifier would be new output whose meaning is not recoverable from the contract — the
`F-V01-9` class of debt, which `UD-019` forbids deepening. It is nonetheless the only family
whose association survives *structural* transformation, so it is not eliminated on merit; it is
eliminated on cost, and that judgement is recorded rather than assumed.

**Family B1 fits the existing output and needs nothing invented** — but it is not free, and two
limits must be stated rather than glossed.

**F-TD-5 — applicability is not provenance, and B1 may satisfy only the first.** `UD-017`
requires that `basis` be "traceable to the evidence that produced the result", and the scope
proposal's own §4 originally required that "a `metadata-match` basis must name the observed
fields it rests on". Those are two different obligations:

| | Question it answers | B1 status |
|---|---|---|
| **Applicability** | *to which entry or object does this `basis` apply?* | **B1 satisfies this**, if enforced |
| **Provenance** | *which evidence did this `basis` rest on?* | **B1 alone does not satisfy this.** A flat `basis=metadata-match` on a path line names the entry but **not** the fields the verdict rested on (size, mtime, `dev`+`ino` — a *set*, not a scalar) |

So the recommendation below is a recommendation **about applicability only**. Satisfying
`UD-017`'s provenance obligation requires a representation that can carry a **set** of observed
fields per result, and a flat scalar field on a line is a poor shape for that. Whether the
provenance obligation is discharged by naming the fields explicitly, by a defined and documented
predicate name that the contract maps to a field set, or by another representation, is
**not decided here** and is not decided by `UD-019` either.

**Second limit — serialization is weaker than it looks.** An intra-line association survives
reordering perfectly but is a property of the *logical* line. If output is captured, wrapped or
re-flowed, an intra-line association can be split across physical lines, and a consumer that
reads physical lines sees a subjectless value — the exact failure EXP-AI-01 recorded. The
contract must therefore state that the logical line is the unit of association. That is a
documentation obligation B1 creates, not a property it has for free.

### E.4 Recommendation (NOT a decision) and what IS decided

> **DECIDED — `UD-020`.** Where `show` exposes a `basis` associated with an entry, `show` must
> identify that entry unambiguously. This is the whole of what `UD-020` decides: it resolves the
> `show` impasse, so that a per-entry value on that surface can be attributable at all. It is
> **not** a redesign of `show` and not a general legibility change.

> **RECOMMENDATION — NOT a decision, and not a `UD`.** For the applicability of `basis` on the
> other surfaces, use **family B1**: emit `basis` on a line that carries its own subject, state
> the rule in the contract, and enforce it with a test. Do not use B2 (scope-by-position) on any
> surface.

The recommendation is offered for review. `UD-019` remains the authority and its question stays
**OPEN**: *"basis must be traceable to the entry or object it applies to. The mechanism of that
traceability remains a design question."* Nothing in this document closes it. In particular:

- B1 is **not** selected as a final mechanism, and no `UD` records it;
- the field's name, and how a path is rendered inside it, are undecided;
- **F-TD-5 is `RESOLVED AT SEMANTIC LEVEL / MECHANISM OPEN`**: its semantics are decided (J.1,
  §E.5) and its mechanism is not; B1 addresses applicability, and `UD-017`'s provenance obligation
  is not discharged by it;
- the serialization obligation B1 creates (logical line as the unit) is an undecided
  documentation requirement, not a settled property.

What `UD-020` settles, and what follows from it:

- **`changes`** — mutation lines carry `path=`; `basis` can join `content-changed` and
  `scan-complete` on the same line without a new subject field.
- **`status` / `observe`** — the counts are aggregates. Any per-`basis` breakdown must be on a
  line that names the run it summarises.
- **`show`** — gains a field naming the entry it reports (`UD-020`). **The change is the minimum
  that makes a per-entry value attributable, and nothing more**: no redesign of `show`, no new
  command, no resolution of `F-V01-8`/`F-V01-9`, no legibility cleanup.
- **`CTF-2` itself remains a deferred legibility debt.** What `UD-020` takes into v0.2 is the
  minimum needed for attributability, not the debt's own resolution. The path-encoding
  declaration (`path-encoding=escaped` naming no path — §E.1 class 2) is **not** resolved by this
  and remains `RESEARCH FOLLOW-UP`.

**One open detail inside `UD-020`'s scope**, recorded so it is not mistaken for settled: whether
`show`'s new entry-naming field and the `path-encoding` note should share a mechanism. `UD-020`
does not decide that, and the path-encoding note is out of its scope.

### E.5 What `UD-017` actually requires — reconstructed, not paraphrased

**F-TD-5 is the subject of E.5–E.11.** It is now **`RESOLVED AT SEMANTIC LEVEL / MECHANISM
OPEN`**: J.1 decided what "traceable" means (§E.5) and deliberately selected no mechanism
(§E.11). E.5–E.11 are the analysis behind that split; they close the semantics and leave the
mechanism open.

`UD-017` makes **two** traceability statements, and they are not the same statement:

| # | Sentence (verbatim) | What it demands |
|---|---|---|
| (i) | "`basis` must be traceable to **the evidence that produced the result**" | a relation from the result to its evidence — **scope undefined** |
| (ii) | "`basis` must remain traceable to **the observed fields it rests on**" | a relation from the result to a **set of fields** — narrower, more concrete |

Plus three further obligations that constrain any answer: the output must **distinguish four
outcomes**; `status` must expose the difference and `show` must expose `basis` where relevant; and
a **contractual test must fail** if a skipped entry is counted again as content-verified. And the
mandatory rule: *if Umbral did not read the bytes, it may not present the result as
content-verified.*

**DECIDED — interpretation (b), 2026-09-13 (owner, "J.1").** `UD-017`'s "traceable" means:

> the result must provide a **reference sufficient to locate, in the durable record, the evidence
> that produced the result.** The output does **not** need to enumerate the evidence's values again.

The two readings were:

- **(a) named in the output** — the output itself states which evidence produced the result;
- **(b) locatable from the output** — the output states a reference sufficient to find the
  evidence, which is then read from the durable record.

**(b) is adopted.** (a) is satisfiable without the log and (b) is not, which is what made them
different products rather than two phrasings of one. The chain the decision fixes:

```
result
  -> evidence reference
  -> durable observation(s)
  -> observed field(s) and values
```

**This is a semantic decision, not a mechanism decision.** What the decision does **not** select,
and this document must not read into it: the field's name; the schema; the encoding; the textual
representation; B1 as the final mechanism; any concrete predicate; the persistence structure. Each
remains `OPEN` (§J).

**`UD-017`(ii) under (b).** "`basis` must remain traceable to the observed fields it rests on"
means four things together, and the fourth is what (b) buys:

1. the contract **determinably identifies which observed fields** constitute the basis;
2. the reference **locates the durable observation** that contains those fields;
3. the **values are reconstructible** from the durable record;
4. those values **need not be duplicated** on every output line.

**`basis` is not reducible to a scalar, and the decision says so.** The evidence may be: multiple
fields; multiple observations; fields from **different paths**; run-level evidence; negative facts;
structural facts. §E.6 enumerates each of these from the code rather than assuming them.

**No new `UD` is created by this decision**, and that is a determination rather than an omission:
adopting (b) resolves an **ambiguity in `UD-017`'s wording**, not a contradiction with any recorded
commitment. `UD-017`'s text, its mandatory rule, its epistemic chain and its scope guard are all
untouched and remain in force; (b) narrows what "traceable" was always going to have to mean for
the record to be checkable. `UD-016`, `UD-019`, `UD-020` and `UD-021` are unaffected. The
interpretation is registered here, referencing `UD-017`, because the historical record is not
edited to carry an interpretation it did not state.

### E.6 The evidence that produced a result, enumerated from the code

The question "is the evidence a scalar or a set?" is answerable from `reconcile.rs` rather than
by argument. For every result the tool produces, the evidence it rests on:

| Result | Evidence it rests on | Observations spanned | Kind of evidence |
|---|---|---|---|
| `Unchanged` (metadata equal) | `kind`, `size`, `mtime`, `dev`+`ino` | **two** (prev, cur) | observed fields |
| `Unchanged` (metadata moved, bytes same) | `dev`+`ino`, `size`, `mtime` **and both hashes** | **two** | observed fields + content readings |
| `Modified` | `size`, `mtime`, `dev`+`ino`, hash inequality or absence | **two** | observed fields + content readings |
| `Created` | presence now **and absence in the previous set** | **two**, one of them negative | observed + a **negative** fact |
| `Deleted` | absence now, **plus the run's `complete`**, plus `object_survives` | one + **a run-level fact** + possibly another entry | negative + run-level + cross-entry |
| `Unobserved` | absence now **plus `complete == false`** | one + run-level | negative + run-level |
| `RenamedOrMoved` | `dev`+`ino` equality **across two different paths** | **two, at different paths** | observed fields, **cross-entry** |
| `Recreated` | `dev`+`ino` difference + hash inequality | two | observed + content |
| `Ambiguous(ConflictingCandidates)` | the **cardinality** of the id groups | two | structural |
| `Ambiguous(DuplicateContentNotIdentity)` | hash equality + `dev`+`ino` difference | two | observed + content |
| `Ambiguous(NoContentEvidence)` | absence of hashes + `dev`+`ino` difference | two | negative + observed |
| `status` count `content-verified=N` | **a set of N entries**, each with a stable reading | **N** | a set, not a field |
| `show` per-run result | that observation's `hash`, `hash_stability`, `kind`, `size`, `mtime` | **one** | observed + content |

**Four conclusions follow, and each is a fact about the existing code, not a proposal.**

1. **The evidence is a set, never a scalar.** No single field names it. Even the simplest case
   rests on four observed fields; an aggregate rests on `N` entries.
2. **The evidence spans up to two observations**, and for `RenamedOrMoved` two observations **at
   different paths**.
3. **The evidence includes non-field items**: negative facts (absence from a set), run-level
   facts (`complete`), and structural facts (group cardinality).
4. **The evidence can reference an entry other than the one the result applies to.** This is the
   decisive point for F-TD-5 and is developed in E.7.

**Durable vs derivable, from the v0.1 schema** (`log/sqlite.rs`, verified):

| Class | Items |
|---|---|
| **Durable** (persisted) | `run_id`, `path`, `kind`, `dev`, `ino`, `size`, `mtime_s`, `mtime_ns`, `hash`, `hashed_len`, `hash_stability`, `hash_deltas`, `obs_error`; and per run: `started_at_ns`, `finished_at_ns`, `root` |
| **Derivable** (computed on read) | `complete` (from the `obs_error` count), `content_changed`, `reason`, `object_survives`, every count, and every `basis` value |
| **Neither durable nor derivable under v0.2** | **the identity of the run that produced a carried content reading** |

That last row is the whole of what v0.2 must add. **Every other item of evidence that `UD-017`
asks to be traceable is already durable in the v0.1 schema.** The requirement is not "persist
more evidence"; it is "restore one piece of provenance that the skip destroys".

**F-TD-8 — a second, distinct consequence the attribution must also cover.** In v0.1, a run's
rows *were* the state of knowledge at that run: every entry was read every run, so `observations
for run N` answered "what was known at N". Under skip that stops being true — a row may carry a
reading older than its own run, so the state of knowledge at run N becomes a function of **all
rows up to N**. That is derivable *if* the attribution exists, and not derivable otherwise. It is
a different obligation from "label this row's basis", and it is the one `check` will have to
implement.

### E.7 Applicability and provenance are two relations — and they are not co-extensive

Two relations, stated separately:

```
A: result -> entry/object            (applicability)
B: result -> set of evidence items   (provenance)
```

Each evidence item is identified by **(observation, field)**, where an observation is
**(run, path)** — not a run alone. `B` may also contain run-level items (`complete`) and negative
items (absence).

**A ≠ B, and the proof is in the code.** Four cases where the evidence belongs to a different
subject than the result:

| Result | A (what it applies to) | B (what its evidence is about) |
|---|---|---|
| `RenamedOrMoved` | the **current** path (`d.txt`) | `dev`+`ino` shared with the observation at the **previous** path (`c.txt`), in an earlier run |
| `Deleted` with `object_survives=true` | the **deleted** path | the surviving object, **at an entry the output does not name** (`F-TD-7`) |
| any mutation line | that entry | **the whole run**, via `complete_scan` |
| `status` count | **the run** (a scope, not an entry) | a **set of N entries** |

So a mechanism that answers A — naming the entry on the line — answers **nothing** about B. They
are two relations and, as the mandate requires, **this document does not assume one mechanism
represents both.**

**What J.1 settles here, and what it does not.** The *semantics* of B are now decided: a result
must provide a reference sufficient to locate, in the durable record, the evidence that produced it
(§E.5). That is a statement about what B must achieve, not about how it is represented. Whether A
and B share a representation, are separate, or are composed **remains a mechanism question**, and
§E.11 recommends a split without deciding it.

**F-TD-6 — the reference must be an observation, not a run. ACCEPTED as a conceptual
requirement.** The schema's key is `PRIMARY KEY (run_id, path)`, so **a run id alone does not
identify an observation**. Under a rename, the carried reading came from an observation at a
*different path*, so a bare `hash_read_run = M` does not locate it: the referenced observation is
`(M, old_path)`, and `(M, current_path)` is a different row — or no row at all. A reference that
names only the run is therefore **incomplete for exactly the case where the reading moved.**

Under (b) this becomes a requirement of the semantics, not a design preference: **a reference to an
observation must be able to distinguish `(run_id, path)`.** `run_id` alone is not sufficient and is
**not** accepted. What is **not** decided: whether that reference is represented literally as a
tuple, a derived identifier, an object, or something else. That is a mechanism choice (§J).

**F-TD-7 — a cross-entry fact must be locatable, not merely stated. ACCEPTED as a requirement.**
`mutation_line` emits `object-survives=true` with no reference to the surviving entry, so its
provenance is **not locatable from the output** — the fact is stated and the evidence for it is
unreachable. Under (b) that is a defect, because locatability is precisely what (b) requires.

Stated as the requirement: **for any result whose evidence rests on an entry other than the
result's own subject, the reference must locate that entry's observation.** It is formulated as a
falsifiable property in §G (**P23**), and it is deliberately *not* stated as "the reference must
name the entry" — naming is one mechanism, and (b) requires only locatability.

**F-TD-8 — four distinct roles, and "run N" must not imply "evidence from N". ACCEPTED as a
requirement.** The four roles are separate and must stay separate:

| Role | What it is | Where it lives |
|---|---|---|
| **result run** | the run whose output carries the result | the run the result is reported under |
| **evidence observation run** | the run of the observation whose fields the result rests on | the reference |
| **content-read observation** | the observation in which the bytes were actually read | the reference, when the evidence is a content reading |
| **metadata re-observation** | the observation in which metadata was re-read and matched, producing a `metadata-stable` result | the current run, and it is **not** a content reading |

Two of these coincide in the common case and **must not be conflated**: a `metadata-stable` result
has a **metadata re-observation in run N** and a **content-read observation in some run M ≤ N**.
Saying "verified in run N" of it is false; saying "re-observed in N" is true. The property that
keeps this honest is **P26** (§G), and the state-of-knowledge consequence is **P24**.

The consequence already recorded stands: under skip, a run's rows are **not** the state of
knowledge at that run, so the state at N is a function of **all rows ≤ N**. That is derivable *if*
the reference exists and not otherwise.

### E.8 B1 reassessed — exact scope of the recommendation

B1 remains a **RECOMMENDATION**, and its scope narrows.

| Question | Does B1 answer it? |
|---|---|
| **A**, for a per-entry result (`changes` mutation lines) | **Yes**, given the subject is on the line — already true (`path=`) |
| **A**, for a per-observation result (`show`) | **Yes**, once the entry is named (`UD-020`) and combined with the `run=` already on the line — so A here is the pair **(entry, run)**, not the entry alone |
| **A**, for an aggregate (`status`/`observe` counts) | **Only as a scope.** The subject is the run; there is no entry. A per-`basis` breakdown must be on a run-scoped line |
| **B**, provenance, any case | **No.** B1 says *which entry a value applies to*. It says nothing about *which evidence produced it*. See E.7 |
| **B** for the mandatory rule's minimum | **No** — that needs the reading's run attribution, which is a different relation (E.9) |

**The recommendation is therefore retained for A only, with that scope stated**, and it is not
extended to B. Two further limits, both already recorded and both unchanged by this analysis:
B1 creates a serialization obligation (the logical line is the unit — E.10), and B1 says nothing
about `F-TD-9`.

**Re-evaluated under the decided semantics (J.1).** With "traceable" fixed as *locatable*
(§E.5), B1's position is unchanged and its limits are now sharper rather than softer:

| | Under J.1 |
|---|---|
| Does B1 satisfy A? | **Yes** — and A is unaffected by J.1, which is about B |
| Does B1 satisfy B? | **No**, and J.1 does not make it do so. (b) requires a **reference to an observation**; B1 is a statement of *which entry a value applies to*. They remain different relations |
| Does B1's per-line form conflict with (b)? | **No** — but it does not help either. A line can carry both a subject and a reference, and the reference is what answers B |
| Is B1 sufficient for the mandatory rule? | **No.** The mandatory rule needs the reading's observation identity, which is B's business, not A's |

**B1 remains a RECOMMENDATION for A. It is not a decision, and J.1 does not promote it.**

### E.9 `hash_read_run` — what it is, and what it is not

**The problem it solves:** the mandatory rule ("if Umbral did not read the bytes, it may not
present the result as content-verified") is only checkable if "read in *this* run" is answerable.
Under v0.1 that was answerable by construction — every row's hash came from its own run. Under
skip it is not, and the attribution restores it. **It is the minimum sufficient provenance for
the mandatory rule, and it is not sufficient for `UD-017`'s (i).**

**What it conceptually is — three candidates, and they are not the same thing:**

| Candidate | Assessment |
|---|---|
| **identity of a reading** (a reading event) | Closest to the concept. A row has at most one content reading, so the reading and the observation coincide **in this schema** |
| **evidence of an observation** (a set of fields) | A reading *is* several fields (`hash`, `hash_stability`, `hashed_len`, `hash_deltas`), so naming it by a run is naming it by one component |
| **a reference to a run** | What the name literally says — and **an incomplete reference**, since a run does not identify an observation (F-TD-6) |

**Recorded doubt, not a rename** (as the mandate requires): the name `hash_read_run` is **too
specific** — it says *run* where the concept is *the observation that produced this reading*, and
it says *hash* where the concept covers the whole reading. It also invites the F-TD-6 error, by
reading as though a run were a sufficient reference. **No rename is made here and no code is
changed**; the doubt is recorded so that the mechanism design addresses the reference's shape
rather than adopting the name's implication.

### E.10 Reordering and serialization — requirements the final mechanism must meet

The mandate's list, each with what it demands of the representation. **Textual adjacency is not
accepted as sufficient evidence anywhere below** unless the contract makes the association
formally determinable and verifiable.

| Transformation | Requirement it imposes |
|---|---|
| entries change order | The association must be **intra-line**. Any scope-by-position fails (E.2) |
| `basis` in another position on the line | The contract must **not depend on field order**. `key=value` pairs must be order-independent |
| automatic parsing | The field grammar must be **stated**, and **a value must not be able to contain the separator** — see `F-TD-9` |
| consumption by another AI | The contract must be available to the reader, or the association must need no inference. EXP-AI-01 showed positional inference is not reliable |
| multiple entries | Per-line association; each result carries its own reference |
| **one observation contains multiple results** | `show` yields one result **per run** for one path, so A there is **(entry, run)** — naming the entry alone is insufficient |
| serialize / deserialize | The **logical line** must be declared the unit of association; a re-flowed output splits an intra-line association |

**F-TD-9 — the separator can appear unescaped inside a value. RETAINED as a relevant contractual
defect.** `mutation_line` joins fields with two spaces, and `escape_path_bytes` escapes only `\` and
non-UTF-8 bytes. **A space is neither**, so a path containing two consecutive spaces passes through
literally and makes the line ambiguous to any parser that splits on the separator. This is
pre-existing behaviour, not something v0.2 introduces — but v0.2's own requirement ("automatic
parsing must work") makes it load-bearing, and adding a further field to those lines does not fix
it.

**Stated abstractly, as the grammar requirement** — deliberately without selecting an encoding:

1. **A valid output must be parseable without ambiguity.** For any output the tool is permitted to
   emit, there is exactly one parse.
2. **A value the contract permits must not be able to collide with a delimiter** unless the
   collision is removed by escaping **or by equivalent framing**. Which of those two it is, and
   what the delimiter is, is a mechanism choice (§J).
3. **The requirement is on the grammar, not on the current output.** It is not satisfied by
   observing that today's fixtures happen not to contain the collision — F-TD-9 is exactly the
   case where they can, and a path is attacker-controlled bytes, not a tool-controlled token.
4. **A delimiter inside a value is not a defect of the value.** A path containing any byte
   sequence is legal; the grammar must carry it, not refuse it.

### E.11 Status of the design for F-TD-5 — semantics decided, mechanism open

The mandate's distinction must be explicit, so it is stated first:

```
TRACEABILITY SEMANTICS: DECIDED   — "traceable" = locatable from the result to durable evidence (J.1)
BASIS MECHANISM:        OPEN      — nothing about how it is represented is decided
```

**DECIDED at the semantic level** (owner, J.1 — §E.5; these are requirements now, not proposals):

1. **B is answered by a reference, not by enumeration.** The output does not re-state the
   evidence's values; it provides a reference sufficient to locate them in the durable record.
2. **A reference to an observation must distinguish `(run_id, path)`.** `run_id` alone is not
   accepted (F-TD-6).
3. **A result whose evidence rests on another entry must make that entry's observation locatable**
   (F-TD-7). Locatable — not necessarily "named".
4. **The grammar must be unambiguous, and a permitted value must not collide with a delimiter**
   without escaping or equivalent framing (F-TD-9). Abstract; no encoding selected.
5. **The four run roles must stay distinct** (F-TD-8): result run, evidence observation run,
   content-read observation, metadata re-observation. "Run N" does not imply "evidence from N".
6. **The state of knowledge at run N is reconstructible from rows ≤ N** (F-TD-8).

**RECOMMENDED — not decided, and not a `UD`:**

7. **Keep A and B as two relations.** Do not overload one field with both. The semantics of B are
   now fixed (1–6 above); whether A and B share a representation, are separate, or are composed is
   a mechanism question, and this recommendation is that they be separate.
8. **Represent B by a predicate name plus an observation reference** — the predicate name's meaning
   defined by the contract as a field set, so a reader with the output alone knows *which fields*
   the result rested on, and the reference locates their values. This is the shape that satisfies
   (b) most directly; it is a recommendation because (b) does not require *this* shape.
9. **`show`'s applicability is (entry, run)**, not the entry alone (E.10). Related to `UD-020`'s
   requirement, which fixes attributability and not the mechanism.

**OPEN — mechanism choices, none of them decided by J.1** (§J):

the field's name; the schema; the encoding; the textual representation of the reference; whether the
predicate name is a field or an enumeration; the persistence structure; and whether B1 is the final
mechanism for A.

**Why not enumerate the evidence in the output.** J.1 resolved this, so it is recorded as a
consequence rather than a preference: a rename line would carry two observations' worth of fields,
and an aggregate would carry `N` entries, so the output would grow with the corpus. Under (b) the
reader without the durable record learns the *field set* and not the *values* — that is the accepted
cost of the decision, and it is stated here so it is not rediscovered as a defect later.

### E.12 The conceptual model

Entities, defined without deciding how any of them is serialized. Each is either **durable** (in the
record), **derivable** (computable from the record and the contract), or **neither** — and the
"neither" column is what v0.2 must fix.

| Entity | What it is | Durable? | Derivable? |
|---|---|---|---|
| **run** | one execution of `observe` over one root | yes (`run` table) | — |
| **observation** | one entry as seen in one run. Identity: **(run, path)** | yes (`observation` row) | — |
| **observed field** | a named field of one observation: `kind`, `size`, `mtime`, `dev`, `ino`, `hash`, `hashed_len`, `hash_stability`, `hash_deltas`, `obs_error` | yes (columns) | — |
| **entry/object** | a filesystem entry (a path) or the object it denotes (`dev`+`ino`) | the path is durable; the object identity is durable per observation | — |
| **result** | one classified outcome produced by a command | no — it is a view | yes, from the record |
| **evidence set** | the set of items a result rests on | **partly** — see below | partly |
| **evidence reference** | what a result carries so the evidence can be located | **no — this is the gap** | **no** |

**The evidence set is a set of items, and an item is not always a field.** Three item kinds exist,
and they are not interchangeable:

| Item kind | Example | How it is located |
|---|---|---|
| **field item** | `size` of the previous observation of `a.txt` | an observation reference + a field name |
| **run-level item** | the `complete` flag of the current run | a **run** reference + a field name — no observation |
| **negative/structural item** | "the path is absent from the previous run's set"; "two candidates share this `dev`+`ino`" | a **run** reference + a predicate — **there is no row to point at** |

That third row is the reason a single reference-per-result cannot work, and it is why the model needs
two reference *categories* rather than one (§E.13).

**Relations, with cardinality, direction, and what must be reconstructible:**

| # | Relation | Cardinality | Direction | Durable / derivable | What must be reconstructible |
|---|---|---|---|---|---|
| **A** | result → entry/object | `1 → 1` for per-entry results; `1 → 1` **pair** `(entry, run)` for `show`; `1 → 1` **run** for aggregates | result → subject | subject derivable from the result's own line | **which** entry/object, and for `show`/aggregates which run |
| **B** | result → evidence set | `1 → 1` set; `1 → 1..n` items; `n` bounded by 2 for mutation results, unbounded for aggregates | result → evidence | reference **not** derivable; field set derivable from the contract; values durable | **which** observations, **which** fields, and (with the record) the **values** |

**A and B have different subjects in general**, and the model must not assume otherwise (§E.7). The
four discriminating cases are already recorded; the mechanism must express all four.

**One entity deliberately not added.** There is no "evidence-set identity" entity. An evidence set
has no independent existence: it is a set of items belonging to one result, and giving it an identity
would create a second thing to keep consistent with the result. The set is denoted by the result.

**One relation deliberately not added.** There is no relation between two results. Results are a view;
relating them would make one result's reconstruction depend on another's, which is exactly the
coupling the design avoids elsewhere (a `changes` line must be reconstructible without reading the
other lines).

### E.13 Observation reference — the alternatives

F-TD-6 requires a reference that distinguishes `(run_id, path)`. Four candidates:

| | Candidate | Stability | Collision | Serialization | Lookup | Fit with the current schema | Evolution |
|---|---|---|---|---|---|---|---|
| **R-A** | **conceptual tuple** — the reference *is* `(run_id, path)`, stated as such | Highest: both components are immutable once written | None: it is the primary key | Needs the path rendered as text (escape contract) | Direct: it is the key | **Perfect** — the key already exists, no new column, no new index | A rename does not move an observation; the tuple stays valid |
| **R-B** | **derived identifier** — e.g. a digest of `(run_id, path)`, or a monotonic row id assigned at write time | A monotonic id is stable; a digest is stable iff the path encoding is | Digest: possible in principle, negligible in practice; **monotonic id: none** | Short and opaque | Needs a new column **and** a new index | Adds a second identity that must agree with the primary key | Good, but it is a new identifier to migrate and to keep in agreement |
| **R-C** | **structured reference** — a composite value carrying `run` and `path` as named parts | Same as R-A | None | Needs a nested grammar the current line format does not have | Same as R-A once parsed | Requires a representation the output does not currently have | Fine, but it is R-A with a wrapper |
| **R-D** | **path-relative reference** — name the run only, and take the path from the result's subject | **Fails**: a run does not identify an observation (F-TD-6) | — | Smallest | Ambiguous | — | Fails |

**R-D is the trap, and it is worth naming because it is the smallest.** "Run N, same path as the
subject" is sufficient in the common case and fails exactly where the reading moved — which is the
case the reference exists for.

**Assessment.** **R-A is the identity; R-B and R-C are representations of it.** The tuple is already
the schema's key, so R-A requires no new identity, no new index, and nothing to keep in agreement.
R-B's only advantage is a shorter output, bought with a second identity that can disagree with the
primary key — a poor trade in a system whose whole claim is that the record is the truth. R-C is R-A
plus a grammar the line format does not have.

**RECOMMENDED — not decided:** the reference *denotes* `(run_id, path)` (R-A). Whether it is
serialized as two fields, as one composite token, or otherwise is a representation choice and stays
open (§E.24). **What is decided by J.1** is only that a run alone is not sufficient.

**A consequence the recommendation must carry: the reference is per-item, not per-result.** A
mutation result's evidence spans **two** observations — the previous run's and the current run's —
and a rename's spans two *paths*. So a single reference per result cannot express the evidence set.
The set carries one reference per item. The output cost of that is real and is quantified in §E.21.

### E.14 Evidence representation — the alternatives

| | Candidate | Applicability | Provenance | Multi-observation | Run-level | Negative / structural | Output size | Parser | AI legibility | Reordering | Serialization | Evolution | Duplication | Testability |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| **M1** | reference + **contract-defined predicate name** | yes | yes | yes, if the contract defines the predicate over a set of observations | yes | yes, by naming a predicate over set membership | smallest | simple | good **only if** the contract is available to the reader | survives | survives | **closed world**: a novel evidence set needs a new predicate + a contract edition | none | easy |
| **M2** | reference + **explicit field list** on the line | yes | yes | yes — each item names its own observation | yes | yes, with a stated marker | larger: a field name per item | simple | good: no contract needed for the field set | survives | survives | **open world**: a novel evidence set needs no contract change | the field list restates what the contract could state | easy |
| **M3** | **inline enumeration** — the values themselves | yes | yes | yes | yes | yes | **grows with the evidence**, unbounded for aggregates | heavier | best in principle | survives | survives | open | **duplicates the durable record** | easy |
| **M4** | reference + **field set implied by the result kind** | yes | **partial** | yes | yes | yes | smallest | simple | good | survives | survives | **fails — see below** | none | easy |

**M4 fails, and the failure is concrete rather than theoretical.** The same result kind can rest on
**different** evidence sets, so the result kind does not determine the field set:

| Result | Evidence set A | Evidence set B |
|---|---|---|
| `Unchanged` | metadata equal — `kind`, `size`, `mtime`, `dev`+`ino` from both observations | metadata moved, bytes same — **both hashes** plus `dev`+`ino` |
| `Modified` | hashes differ — `size`, `mtime`, both hashes | no hash evidence — `size`, `mtime`, and the **absence** of a comparable hash |

So a reader given only the result kind cannot know which fields the result rested on. **M4 is
eliminated by the code, not by preference.** (The current output does distinguish the two `Unchanged`
sets — `content-changed` is present for one and absent for the other — but that is an
absence-means-something signal, the same class of implicit convention this project rejects
elsewhere.)

**M3 is eliminated by J.1 and by cost.** J.1 decided the output need not re-enumerate the values, and
for an aggregate the enumeration is `N` entries long.

**The mandate's distinction is the discriminator between M1 and M2.** "The reader can find the
evidence" (satisfied by the reference) and "the reader knows which fields form the basis" (needs
either a contract-defined predicate or an explicit list) are two conditions, and **both must hold**.
M1 satisfies the second through the contract; M2 through the line. That is the whole difference
between them.

### E.15 Predicate semantics — analysed, not adopted

The current recommendation is "a predicate name whose meaning the contract defines as a field set".
Analysed on its own terms:

| Question | Answer |
|---|---|
| **What problem does it solve?** | It states the field set in one token, so the output stays small and the mapping lives in one place |
| **What information does it lose?** | The values (accepted by J.1). It also loses **self-description**: the field set is not recoverable from the output alone |
| **Fields from several observations?** | Yes, if the contract defines the predicate over a set of observations rather than one — but the *predicate name alone* then does not say which observation supplies which field, so the items' references must carry that |
| **Negative evidence?** | **Only awkwardly.** A predicate can *name* "absent from the previous run's set", but there is no observation to reference, so the predicate must be paired with a **run** reference rather than an observation reference. The predicate and the reference must therefore be able to disagree in kind |
| **Structural evidence?** | Same answer: cardinality is a fact about a run's set, not a field of a row |
| **Can two results have different evidence sets?** | Yes — and this is why M4 fails (§E.14). The predicate is what distinguishes them |
| **Must the contract version the predicates?** | **Yes, and this is the unaddressed gap — F-TD-10.** |

**F-TD-10 — the output declares no contract version, so a contract-defined predicate name is not
resolvable from the output alone.** A predicate's meaning is fixed by the contract, and the contract
changes with the version. A reader holding a newer or older contract reads the same token as a
different field set. The log declares a schema version (`umbral-v0.1` in `schema_meta`); **the
command output declares none.** So M1's "the contract defines it" is not sufficient as stated: the
reader must also know *which* contract. This is a real defect of the M1 recommendation, found by
analysing it rather than by adopting it, and it is the reason M2 is a serious competitor: an explicit
field list is self-describing and needs no version.

**Not adopted.** The predicate form is a recommendation with a named cost (self-description and
version dependence) and a named competitor (M2). §E.23 recommends a combination, and it is not a
decision.

### E.16 Applicability under the full model

B1 is re-evaluated against every surface the mandate names. **One representation is not sufficient**,
and the reason is that the subject is not always an entry.

| Surface | Result | Subject (A) | Is B1 sufficient? |
|---|---|---|---|
| `changes` | mutation line | the entry at `path=` | **Yes** — the subject is on the line |
| `changes` | `RenamedOrMoved` | the entry at the **current** path | **Yes for A.** B is different: the evidence includes the observation at the **previous** path (§E.17) |
| `changes` | `Deleted` + `object_survives=true` | the **deleted** path | **Yes for A.** B references the surviving object, at a path the line does not name (§E.17) |
| `show` | per-run result | the pair **(entry, run)** | **Yes, with `UD-020`** — and only as the pair. The entry alone is insufficient because `show` yields one result per run |
| `status` / `observe` | aggregate count | **the run** — a scope, not an entry | **Only as a scope.** There is no entry to name; a per-`basis` breakdown must sit on a run-scoped line |

**Conclusion: applicability needs two conceptual categories, not one.**

1. **Entry-scoped** — the subject is an entry, or the pair `(entry, run)`. Covered by B1, already
   present in the output for `changes`, and reachable for `show` via `UD-020`.
2. **Run-scoped** — the subject is a run, and the result is an aggregate over that run's observation
   set. B1 does not apply: there is no entry to put on the line, and putting a run on the line is a
   different statement.

**This is a conceptual distinction, not an output-syntax decision.** B1 remains the recommendation
for category 1, and category 2 needs its own answer — which is why `status`'s per-`basis` breakdown
was flagged in §E.4 as needing a run-scoped line. That requirement stands and is now grounded: it is
not a formatting convenience, it is the second applicability category.

**B1's status is unchanged: RECOMMENDATION, for category 1 only.**

### E.17 F-TD-7 resolved conceptually — cross-entry provenance

The requirement is that evidence belonging to another entry be **locatable**. The two mandatory
examples:

**Example 1 — `RenamedOrMoved`.** Result applies to `d.txt`; evidence includes the observation of
`c.txt` at run M. The evidence set is:

```
item 1: observation (M, c.txt)  · fields dev, ino
item 2: observation (N, d.txt)  · fields dev, ino
```

Both items are **field items**; both carry their own observation reference; **neither is the
result's subject**. The result's subject is `d.txt` at the current run, which coincides with item 2's
observation but not with item 1's.

**Example 2 — `Deleted` + `object_survives=true`.** Result applies to the deleted path `a.txt`;
evidence is that `a.txt`'s `dev`+`ino` **still appears** in the current run's set, at some entry the
output does not otherwise name. The evidence set is:

```
item 1: observation (M, a.txt)  · fields dev, ino        [the vanished entry]
item 2: run N                    · predicate: some entry in N carries this dev+ino
```

Item 2 is a **run-level item with a structural predicate**, not a field item: what supports the fact
is a property of the run's whole set, not a field of one row. Under the model of §E.12 that is
expressible — it is the third item kind.

**Resolution: no new relation is needed, and no "cross-entry" concept is needed either.** Both
examples are already expressible once the model has (i) per-item observation references and (ii) a
run-level item kind. **The only thing that was missing was the willingness to let an item's
observation differ from the result's subject** — which is a statement about the model, not a new
entity.

**What this rules out**, and it is worth recording because it is the tempting shortcut: a
"primary/auxiliary" split in which the result carries one reference to its own observation and the
rest are described as "related". That would make the auxiliary evidence second-class and would leave
`object_survives` — whose evidence is *entirely* auxiliary — with nothing to point at.

### E.18 F-TD-8 resolved conceptually — the four runs, and what must persist

The four roles, restated as a formal distinction:

| Role | Definition | Where it comes from |
|---|---|---|
| **result run** `R_r` | the run whose output carries the result | the result's own line |
| **evidence observation run** `R_e` | the run of the observation supplying a field item | the item's observation reference |
| **content-read observation** `C` | the observation in which the bytes were actually read | the item's reference, when the item is a content field |
| **metadata re-observation** `M` | the observation in which metadata was re-read and matched | the result run `R_r` itself |

**The rule the model must enforce:** `R_r = R_e` is **not** implied. For a `metadata-stable` result,
`M = R_r` while `C = R_e < R_r` — the same result has a re-observation in the current run and a
content reading in an earlier one. Saying "verified in run N" of it is false; saying "re-observed in
N" is true.

**What must be persisted for run N's state to be recomputable.** The state of knowledge at N is a
function of the record up to N. For each observation row, what is needed is:

| Needed | Already persisted? |
|---|---|
| the row's own observation — `(run_id, path)` and its fields | **yes** |
| the run's `complete` flag | **derivable** from the `obs_error` count |
| **the identity of the observation that supplied a carried reading** | **no — the gap** |

So the persistence requirement is narrow and it is one item: **enough to identify the evidence
observation of any field item, which is `(run_id, path)`.** For a fresh read the evidence observation
*is* the row itself, so the value is trivially derivable; for a carried reading it is not derivable
at all and must be stored.

**Two ways to satisfy it, and the difference matters:**

- **store the reference on every row**, including the fresh case where it equals the row's own key;
- **store it only where it differs**, with absence meaning "own observation".

The second is smaller and **is not recommended**, for the same reason recorded elsewhere in this
document: absence-as-meaning is an implicit convention, and it is exactly the class of signal that
produced EXP-AI-01's Q2 divergence and that §E.14 rejects for M4. Whether the schema nevertheless
takes the smaller form is a **schema decision and stays open** (§E.24) — but the *semantics* must not
depend on absence meaning anything.

**One consequence for `check`.** Because a run's rows are no longer the state of knowledge at that
run, `check` must reconstruct each entry's basis at each run **from all rows ≤ N**, applying the
`R_r = R_e` rule per row. That is P24 and P26, and it is a different computation from the one v0.1's
`check` performs.

### E.19 F-TD-9 and F-TD-11 — the grammar

**F-TD-11, found while analysing the escaping for this section: a path containing a newline breaks
the line unit itself.** `escape_path_bytes` pushes every byte `< 0x80` literally except backslash
(`b < 0x80 → out.push(b as char)`), and `0x0A` is both `< 0x80` and not a backslash. So a path
containing a newline is emitted literally, and **the output line is split in two**. This is worse than
F-TD-9: F-TD-9 makes a *line* ambiguous to a parser that splits on the delimiter, while F-TD-11
destroys the line boundary that §E.10 declares to be the unit of association. If the line cannot be
identified, no association can be made from it. Verified against the code; **no test covers it** — the
suite exercises non-UTF-8 names and backslashes, not control characters.

**The required property, restated for both:** for any output the tool is permitted to emit, there is
exactly one parse, and that parse yields the same semantic associations. F-TD-11 shows the property
must be stated over the **line terminator** as well as the delimiter.

**Alternatives:**

| | Approach | Unambiguous? | Human reading | Parser complexity | Fit with the current output | Cost |
|---|---|---|---|---|---|---|
| **G-1** | **delimiter + escaping** — state the delimiter, escape it in values | yes, if the escape covers the delimiter **and** the line terminator | unchanged | low: one unescape | smallest change; keeps the key=value line format | an escape function defined over **values**, not paths |
| **G-2** | **length framing** — prefix each value with its length | yes, without escaping | poor: `path=12:notes/foo` is hard to read | medium: length parsing, and a wrong length desynchronises the rest of the line | a new convention on every field | framing on every value |
| **G-3** | **structured representation** (e.g. one object per line) | yes | poor for a terminal surface | high | replaces the output format | a wholesale format change, and the project's output is deliberately line-oriented |
| **G-4** | **field per line** — one field per line, no delimiter | yes for the delimiter | poor: it re-introduces "which result does this line belong to" | medium | breaks the current shape | **fails §E.10**: it restores positional association |

**G-4 fails on principle, not on cost:** it solves the delimiter problem by making the association
positional again, which is the failure EXP-AI-01 recorded and §E.10 forbids.

**RECOMMENDED — not decided: G-1**, because it is the smallest change to an output format that is
already documented as reversible for paths, and it preserves the line-oriented human surface. **Its
cost is named and it is not cosmetic:** the escaping must be redefined at the **value** level. Today's
`escape_path_bytes` is *path*-specific — it escapes backslash and invalid UTF-8, and nothing else.
A value-level escape must cover the delimiter and the line terminator too, which means **a path
containing a newline would render differently after this change than before it.** That is a visible
output change and it belongs in the version record.

**No encoding is selected here.** G-2 and G-3 remain legitimate; the recommendation is that the
grammar be defined over values, whichever framing is chosen.

### E.20 Serialization and transformation — what each candidate survives

Applied to the recommended combination (R-A reference, per-item, with an M1/M2-style field set under
G-1 grammar). Each row states whether the *association* survives.

| Transformation | M1 (predicate) | M2 (explicit list) | M3 (inline values) | Why |
|---|---|---|---|---|
| **reorder lines** | survives | survives | survives | the association is intra-line |

| **move the reference's position on the line** | survives | survives | survives | key=value pairs are order-independent **provided the contract says so** — a requirement, not an accident |

### E.21 Cost model — conceptual, no benchmarks

Estimates are **orders and directions, not measurements.** No benchmark was run, and none of these
numbers may be quoted as one.

| Dimension | Inline enumeration (M3) | Reference-based (M1/M2) |
|---|---|---|
| **output growth per mutation result** | ~8–12 field values, two observations' worth | ~2 references + a field set: smaller, and **bounded** |
| **output growth per aggregate** | **`N` entries** — grows with the corpus | constant: the run is named, not the entries |
| **log growth** | none beyond today | **one reference per observation row**, i.e. the identity of the evidence observation. Two components (`run_id`, `path`), the second already present as the primary key's second column — so the marginal cost is small but nonzero |
| **reconstruction cost** | none: the values are on the line | one indexed lookup per item. The index on `path` exists; a lookup by `(run_id, path)` is the primary key, so it is a point lookup |
| **parser complexity** | low | low, **plus** the grammar work of F-TD-9/F-TD-11 |
| **implementation complexity** | low — render what is in memory | medium: the decision must carry the reference through reconciliation, and the reference must be persisted |
| **migration cost** | none | v0.1 rows need the reference derived. For v0.1 this is **safe**: every row was read in its own run, so the evidence observation is the row itself. Deriving it is not a guess — it is what v0.1's behaviour guarantees |

**The comparison that matters is the aggregate row.** Inline enumeration grows with the corpus and is
therefore not viable at all for `status`; a reference is constant. That single row decides the
comparison independently of every other column.

**Second observation.** The log-growth row is the only place where the reference-based design is
larger, and it is larger by one small tuple per row, against a saving that is unbounded on the output
side. The trade is favourable and it is the trade J.1 already made.

### E.22 Security and authority — checked, not assumed

| Property | Assessment |
|---|---|
| **Grants authority** | **No.** A reference is a pointer. It carries no permission, and the read-only commands still open the state file with `SQLITE_OPEN_READ_ONLY`. |

### E.23 Recommended mechanism — a RECOMMENDATION, not a decision

Offered for review. It decides nothing and creates no `UD`.

**The mechanism, in one paragraph.** A result carries an **evidence set** whose items each carry a
**self-contained observation reference denoting `(run_id, path)`** (R-A), or a **run** reference when
the item is run-level; the **field set** is stated either by a contract-defined predicate or by an
explicit field list (§E.14's M1 vs M2, still open); and the whole thing is written in a grammar whose
escaping is defined **over values** (G-1). Applicability stays B1 for entry-scoped results and is a
run-scoped statement for aggregates.

**Decided conceptually** (by J.1, §E.5–E.11, restated here as what the mechanism must satisfy):

1. B is answered by reference, not enumeration.
2. A reference must distinguish `(run_id, path)`.
3. Cross-entry evidence must be locatable.
4. The grammar must be unambiguous for permitted values.
5. The four run roles must stay distinct.
6. State at run N is reconstructible from rows ≤ N.

**Recommended, not decided:**

7. **R-A** — the reference denotes the tuple `(run_id, path)`, not a derived id.
8. **Per-item references**, not one per result.
9. **Self-contained references** — no elision of the path when it equals the subject. *Why:* eliding
   would make B's resolvability depend on A's correctness, and the two relations are required to be
   independent. *Cost:* a path per item on the line, accepted.
10. **Two applicability categories** — entry-scoped (B1) and run-scoped.
11. **G-1** — delimiter plus a value-level escape covering the delimiter and the line terminator.
12. **A field set that is self-describing or version-pinned.** This is where M1 and M2 are
    reconciled rather than chosen: if the predicate form is used, the output must carry something
    that identifies the contract edition (F-TD-10); if the explicit-list form is used, it need not.
    **Either satisfies the requirement; the choice is open.**

**Trade-offs accepted, stated rather than hidden:**

- the reader without the durable record learns the field set and not the values (J.1's cost);
- the output grows by roughly one reference per evidence item, and for mutations that is two;
- the escape contract changes visibly for paths containing control characters (F-TD-11);
- a reference that does not resolve yields no evidence — a new failure mode, failing closed.

**What this recommendation does not do:** it does not design the schema, does not select M1 or M2,
does not select a field name, does not select the textual form of the reference, and does not
authorize implementation.

### E.25 The semantic unit — the line is a representation, not the unit

**The assumption under examination.** §E.10 declared the *logical line* the unit of association.
That declaration conflated two things, and the grammar phase must separate them: **the unit of
association** and **the unit of textual rendering**. The first is semantic; the second is
presentational; and F-TD-11 is exactly what happens when the second is allowed to define the first.

**The semantic unit is the result**: one classified outcome together with (i) its subject
(applicability, A) and (ii) its evidence set (provenance, B). Every property the contract requires
— subject determinable, evidence locatable, associations stable — is a property *of a result*.
A line is merely how a result has been rendered so far.

**What follows from keeping the two apart:**

- **Re-flow and line wrapping are not semantic transformations and must not be able to change
  meaning.** A transformation that wraps a rendered line at a terminal's width is a property of the
  *display*, not of the output; the contract must state that meaning is carried by the serialized
  result, never by where a renderer happens to break a row of text. §E.10's "reflow" row survives
  only because the contract declares the logical line the unit — this section restates that
  obligation at its correct level: **the unit is the result; a correct serialization makes the
  result's boundaries determinable regardless of rendering.**
- **Terminal rendering must not be load-bearing.** No association may depend on column position,
  colour, or where a terminal chooses to wrap. This was already the lesson of EXP-AI-01
  (positional adjacency failed two independent readers); it is now stated as a requirement on the
  grammar rather than as advice.
- **The unit's boundary must be carried by the serialization itself.** A reader must be able to
  determine where one result ends and the next begins from the grammar, not by counting display
  rows. This is the requirement F-TD-11 violates today: a newline inside a value destroys the only
  boundary marker the current format has.

**Restated obligation, superseding the "logical line" phrasing where they differ:** the contract
must define a **result delimiter scheme** that cannot be produced by any value — whether by
escaping (G-1), framing (G-2), structure (G-3) — so that *result boundaries are unambiguous for
every valid value*. The rendered line remains the expected presentation for humans; it ceases to be
the definition of the unit.

### E.26 F-TD-11 formalized as a contract requirement — not a newline patch

**F-TD-11 (general form):** *every value the contract's domain permits must be serializable
without destroying boundaries, identity, associations, or parseability.* The domain includes,
explicitly and non-exhaustively: control characters (newline, carriage return, tab, other
`< 0x20` and `0x7F`), whitespace of any run length, backslash, non-UTF-8 bytes, bytes equal to any
current or **future** delimiter, and **every combination of these**.

**Four sub-requirements, each independently falsifiable:**

1. **Boundaries** — a value must not be able to create or erase a result boundary. The newline
   case is one instance: today `escape_path_bytes` passes `0x0A` through literally (`b < 0x80`
   branch, not a backslash), so a path containing it splits one result across two physical lines.
2. **Identity** — serialization must be injective on the domain: two different values must never
   render identically, and one value must have exactly one rendering. The backslash case is the
   trap: an escape scheme that escapes the escape character but not the delimiter produces two
   preimages for one rendering (see §E.28's G-1 requirement).
3. **Associations** — after serialization and parsing, every association (result → subject,
   result → evidence items) must be identical to what the producer held.
4. **Parseability** — the parse must exist and be unique: for every valid output there is exactly
   one derivation under the stated grammar.

**The general property** (see P34–P35, §G.2d) is stated over the **whole domain**, and its
falsifier is always a **valid** value — a path the tool is permitted to observe — never malformed
input. This is what distinguishes a grammar defect from ordinary error handling: the current
escape passes backslash and non-UTF-8 (the cases the original author anticipated) and fails
newline and the delimiter (the cases it did not). A requirement stated over anticipated cases is
not a requirement; §E.25's domain statement is.

### E.27 Grammar comparison — full criteria

The four families of §E.19, now evaluated against the full criterion set. G-5 is added: it is not
a new *family*, but a **discipline** the chosen grammar must adopt regardless of family.

| Criterion | **G-1** delimiter + escaping | **G-2** length framing | **G-3** structured (one object per result) | **G-4** field-per-line |
|---|---|---|---|---|
| parseability | unique **iff** escaping is complete over the domain (F-TD-11 shows today's is not) | unique | unique | unique per field; **association across fields is positional** |
| round-trip | injective **iff** the escape character itself is escaped | injective | injective | injective per field |
| control characters | carried **iff** the escape covers them | carried natively | carried natively | carried natively |
| arbitrary bytes | carried via `\xNN` (exists today for non-UTF-8) | carried natively | carried natively | carried natively |
| whitespace runs | carried **iff** escaped (F-TD-9) | carried natively | carried natively | ambiguous for display, fine for parse |
| nested/multiple evidence items | must define item separator + escape it too — **recursion**: every new delimiter re-opens the problem one level down | carried (items as framed sequences) | natural | positional |
| human readability | **best** — output stays the current shape | **poor** — `path=12:notes/foo` | **poor** for a terminal surface | **poor** — re-introduces "which result does this row belong to" |
| AI readability | good **with the contract stated** | medium | good | poor — positional (the EXP-AI-01 failure) |
| implementation complexity | low-medium: one escape function over values, applied everywhere | medium: framing on every value; a wrong length desynchronises the rest of the line | high: replaces the output layer | medium |
| compatibility with current CLI | **highest** — key=value lines preserved | new convention on every field | none — wholesale format change | breaks the current shape |
| evolution | new delimiters require re-opening the escape definition (mitigated by G-5's canonical form) | lengths are grammar-independent | structures evolve naturally | fields evolve positionally — **breaks old parsers** |
| error handling | detectable: invalid escape sequences are syntactically findable | detectable: length mismatch | detectable: schema validation | silent drift |
| robustness to reflow | survives at result granularity **if** boundaries are escaped | survives at result granularity | survives | survives per field; **association breaks** |
| robustness to reorder | survives (intra-result association) | survives | survives | **fails** (positional) — §E.10, EXP-AI-01 |
| security implications | escape must be proven injective; rejection of invalid sequences must be explicit (fail-closed) | length fields are trusted input — a hostile length can over-read or desynchronise; bounds-checking is mandatory | parser complexity is attack surface | none beyond positional failures |

**G-4 is eliminated on principle** (§E.19: it restores positional association — the recorded
EXP-AI-01 failure). **G-3 is not eliminated, but its cost is a new output format**, which is a
product decision above this document's authority to make implicitly; it remains the
cleanest-looking option only if the human-facing line format is considered disposable, and the
project has never decided that.

**G-5 — the canonical-form discipline.** Independently of family, the grammar should define:
(i) a **total order or canonical rendering** for each value, so one value has exactly one
serialization; (ii) a **single escape character with that character itself escaped first** —
the classic inversion that makes the escaping injective by construction (today's function escapes
backslash first and is correct on that axis; its failure is coverage, not ordering);
(iii) **explicit rejection** of syntactically invalid sequences (a dangling `\x` prefix, an
unknown escape) — never a guess.

**DECIDED — G-1 + G-5, 2026-09-13 (owner, product-decision mandate; recorded as `UD-022`).**
The grammar family is
**G-1 (delimiter + escaping) together with the full G-5 discipline**: canonical rendering per
value; a formally defined escape; the escape character itself escaped; **coverage of the whole
valid domain** — newline, CR, tab, other control characters, consecutive whitespace, backslash,
non-UTF-8 bytes, delimiter bytes, and their combinations, explicitly **not** limited to the
current fixtures; and explicit rejection of invalid escape sequences. The adopted contract
property is PC-1/PC-2 (§E.28). **What stays open: the exact escape specification** — the concrete
escape function, its coverage table, and the canonical rendering rules are the remaining
technical specification, deliberately separated from this decision. The semantic unit restated in
§E.25 travels with the decision: **the unit is the result; the line is only a textual
representation; result boundaries are defined by the grammar, not by terminal rendering.**

**DECIDED — G-3 NOT adopted for v0.2 as the primary output (`UD-022`).** Registered as a **valid
alternative that this version does not select**: it is not declared technically invalid, and the
reason for not selecting it is the product decision to keep the existing textual/human-facing
surface. **G-4 remains eliminated on principle**, unchanged.

### E.28 The grammar property — round-trip over the domain

Restating the mandate's property in checkable form. **PC-1 (value round-trip):**

```
for every valid value V in the contract's domain:
    parse(serialize(V)) == V
```

**PC-2 (structure round-trip):**

```
for every valid result R (subject + evidence set + all fields):
    associations(parse(serialize(R))) == associations(R)
```

**Falsifiers — always valid values, never malformed input:** V containing a newline; containing a
carriage return; containing two consecutive spaces (today's delimiter); containing a tab; containing
a backslash followed by an escape-relevant byte; containing non-UTF-8 bytes; containing bytes equal
to a future delimiter; **and pairwise combinations** of these. A grammar that passes every
single-case test and fails one combination does not satisfy PC-1 — combinations are where today's
escape would fail first (a backslash before a newline: escaped backslash, raw newline).

These become **P34–P35** (§G.2d). Note what they give that P25/P30 do not: P25/P30 say *whether a
line parses*; PC-1/PC-2 say *whether the parsed value is the value that was meant* — identity, not
just boundary.

### E.29 Error semantics — fail-closed, no silent recovery

What happens on each malformed condition is part of the contract, and the design rule is stated
once: **if the input cannot be reconstructed unambiguously, no association may be invented.**
Error handling is not a robustness nicety here; it is the same fail-closed direction §E.22
identified for unresolvable references, extended to parsing.

**Error semantics — DECIDED as part of the contract, 2026-09-13 (owner, product-decision
mandate; recorded as `UD-022`).** The table below is adopted, with one addition from the mandate: *no silent
resynchronization* and *no best-effort reinterpretation* are named as standing prohibitions, and
the unknown-grammar-version row is adopted verbatim (reject with explicit reason). What remains
open is only how each rejection is *worded* in the output — a rendering detail, not a semantic
one.

| Condition | Required behaviour | Prohibited behaviour |
|---|---|---|
| malformed escape (dangling `\x`, unknown escape name) | **reject the input with a parse error** naming the position | decode a byte anyway; emit `\x` literally and continue |
| truncated framing (G-2: length exceeds remaining input) | **reject**, naming the field | read what is available; pad; resynchronise at the next plausible delimiter |
| invalid structure (field with no `=`; value missing where the contract requires one) | **reject** | skip the field; default it |
| unknown future field (a well-formed `key=value` whose key the reader's contract edition does not define) | **preserve without interpreting** — the field is carried as opaque data, never silently dropped, never guessed at | drop it; reinterpret it under a near-miss name |
| unknown future grammar version (see §E.31's versioning) | **refuse to interpret, and say why** — the reader states it cannot parse this version; it never attempts a best-effort parse | parse under the old grammar and emit results that look valid |

The unknown-field row is deliberately more permissive than the others, and the reason is evolution:
a grammar whose readers reject every future field makes every addition a breaking change. The
line between *preserve without interpreting* and *reinterpret* is where forward-compatibility
lives, and it must be written down, not improvised per reader.

### E.30 Serialization, transformation and reflow — revisited under the semantic unit

§E.20's table survives, with one correction and one strengthening. **Correction:** its "reflow"
row said associations survive "only at logical-line granularity"; under §E.25 the correct
statement is that reflow is **not a semantic transformation at all** — a grammar satisfying
PC-1/PC-2 survives arbitrary wrapping because meaning never lived in the physical line. **Strengthening:** the "path containing a newline" row — the row where every candidate failed — is now a
**requirement on the grammar** (F-TD-11, §E.26) rather than an observation: whichever family is
chosen must carry a newline-bearing value across a serialize/parse cycle with identity intact.
Under G-1 that means escaping the line terminator; under G-2/G-3 it holds natively. The
candidate-selection consequence is unchanged: **the grammar decision precedes the evidence-representation decision**, because the representation is written into the grammar and a grammar
that cannot carry an arbitrary path cannot carry a reference containing one.

### E.31 Versioning — four functions that must not share one number, and F-TD-10

**First, the separation the mandate demands.** "Version" is doing four distinct jobs in this
system, and collapsing them is how a schema change silently becomes an output-contract change:

| Function | What it governs | Where it lives today | Failure if conflated |
|---|---|---|---|
| **output/contract grammar version** | how output is parsed: fields, delimiters, predicate names | **nowhere — F-TD-10** | a reader applies last year's contract to this year's output and reads a different field set under the same predicate name |
| **durable schema version** | how the log is read: tables, columns | `schema_meta` (`umbral-v0.1`) | a migration guard fails to fire because the output number moved |
| **project version** | release identity | git tags, `Cargo.toml` | cosmetic release bumps invalidate parsers |
| **implementation version** | build identity | git SHA | readers pin to a build instead of a contract |

**One number cannot serve all four** because they change on different schedules and for different
reasons: a predicate definition can change in a documentation commit without any schema or release
change; a schema migration can leave the output grammar untouched. The contract version must
therefore be **its own declared thing**, changed only when the contract's meaning changes.

**F-TD-10's question: how does a reader know which contract edition it is interpreting?**

| Option | Mechanism | Standalone output | Pipes | Saved output | AI consumption | Serialize/deserialize | Evolution |
|---|---|---|---|---|---|---|---|
| **V1** | version **on every line** | yes — self-contained everywhere | yes | yes | yes — no context needed | yes | per-line cost; noisy |
| **V2** | version **in a header** (one line before the results — the output already has a `run=…  root=…` header line, so the slot exists) | yes, if the header always travels with the body — true for `save`, true when a pipe is treated as one stream | yes as a stream | yes | yes, provided consumers are taught to read the header first | yes | one line, cheap |
| **V3** | contract held **externally** (reader supplies the edition) | **no** — a saved output without its contract is uninterpretable at a later date | no | no — the pairing is lost exactly when archives are read | no — the AI must be handed a contract that the output itself does not name | no | cheap now, broken later |
| **V4** | self-describing values (M2-style: every field list explicit, no contract lookup needed) | yes for the *field set* | yes | yes | yes | yes | does not cover grammar-level changes (delimiters, structure) — it removes one dependency, not all |

**V3 is eliminated for the standalone case**, which is the case the project itself cares about:
EXP-AI-01's readers were given output without narration, and the owner's determinability criterion
requires the association to be recoverable from the output plus the contract **as delivered**. An
edition that must be fetched out-of-band fails that criterion for any output read after its
producer's context is gone.

**Assessment — not a decision.** **V2 is the strongest candidate**: it is cheap, it fits the
existing header line, and it covers grammar-level evolution that V4 cannot. **V1 is its
degenerate form** (every line self-contained) and remains legitimate if per-line robustness is
demanded — e.g. output lines are expected to be extracted individually by third-party tools, a
real pattern for `grep`-style consumption. **V4 is not an alternative to V1/V2 but a layer over
them**: even with explicit field lists (M2), a *grammar* change still needs a version marker, so
V4-without-V2 leaves F-TD-10 half-open. The recommendation, accordingly: **a contract/grammar
version in the output header (V2), independent of the schema version, project version and build
identity — with V1's per-line form held as the fallback if individual-line extraction becomes a
requirement.** Whether the version mark is emitted always or only when the basis mechanism is in
play is a scope question left open.

**DECIDED — V2, 2026-09-13 (owner, product-decision mandate; recorded as `UD-022`).** The contract-versioning
mechanism is **V2: an explicit contract/grammar version in the output header**, under the
**strict separation** the analysis established — output contract/grammar version ≠ durable
schema version ≠ project version ≠ implementation version, and one number must not serve all
four. A reader must be able to determine which grammar an output follows from the output/header
alone; **standalone outputs do not depend on the external environment to be interpretable.** V1
is recorded as the fallback if per-line extraction becomes a requirement; V3 stays eliminated;
V4 stays a layer, not an alternative. **What stays open: the exact header representation and the
version value** — the mandate explicitly defers choosing the literal version number until how it
fits the existing nomenclature (`umbral-v0.1` in `schema_meta`, git tags, `Cargo.toml`) is
resolved. That is a naming-convention question, registered as open (§J), deliberately separated
from the mechanism decision.

### E.32 M1/M2 reassessed — under the grammar, not instead of it

Now, and only now, the field-set carrier — because F-TD-10's resolution changes M1's standing:

| Criterion | **M1** predicate name + contract | **M2** explicit field list in the output |
|---|---|---|
| self-description | **no** — the field set lives in the contract edition | **yes** |
| version dependence | **total** — unresolvable without F-TD-10's mechanism; with V2, resolvable | **none** for the field set (grammar version still needed) |
| output size | smallest — one token | larger — grows with item count |
| aggregate growth | **constant** | grows with evidence-item count — bounded for per-entry results, **unbounded only if aggregates ever carry per-entry evidence** (they do not under §E.16: aggregates are run-scoped) |
| multiple observations | carried by the references, not the predicate | same |
| negative evidence | predicate must be defined per absence-predicate | expressible inline (`absent-from:run-M`) |
| structural evidence | predicate per structural fact | expressible inline, more verbose |
| AI legibility | requires contract edition retrieval — one more step than M2 | immediate |
| parser complexity | lowest | low |
| future evolution | predicate definitions can evolve under one version mark — **but a reader with the wrong edition silently mis-reads** (the F-TD-10 trap) | lists evolve freely; old outputs remain readable forever |
| contract compatibility | every predicate change is a contract-version change | no contract lookup at all |

**The comparison has moved.** Before F-TD-10, M1 won on size with a hidden liability. With V2,
M1's liability becomes a managed dependency — the reader resolves the predicate through a versioned
contract, and the failure mode when the contract is missing is *detectable* (unknown version →
refuse, §E.29) rather than silent. M2's advantage is independence; its cost is size, and the size
argument against it was always weakest exactly where M1 is weakest too (aggregates, where neither
grows because aggregates carry run-scoped applicability only).

**Status: both remain viable; neither is recommended here.** The reason for refusing to break the
tie is recorded: the choice trades output size against standalone self-description, and **which of
those the project values more is a product judgement, not a grammar deduction** — the grammar phase
was mandated to close the grammar *before* this question, and it has: whichever is chosen, it is
written into the G-family grammar chosen above and pinned by the version mechanism of §E.31. What
this phase **does** establish: **M1 without a version mechanism is eliminated** (F-TD-10), and
**M2 never needed one for the field set, but still needs the grammar version** (§E.31's V4 row).

- **M1** = contract-defined predicate + evidence reference.
- **M2** = explicit field set + evidence reference.
- **M5 (new) = hybrid**: a predicate for the field sets the contract defines (the common cases),
  plus an explicit field list on results whose field set no defined predicate covers (the
  negative/structural tail). One carrier per line, chosen by rule, never by position.

| Criterion | **M1** | **M2** | **M5 (hybrid)** |
|---|---|---|---|
| standalone comprehensibility | field set only via the contract edition — identifiable (V2) but not *present* | **full** — every line self-describing | full **for every line that carries a list**; predicate lines still need the contract |
| AI consumption | reader must hold or fetch the contract edition; one indirection | **immediate** | immediate for the list-carrying tail only |
| human readability | smallest token; least noise | longest lines | medium |
| output growth | minimal, constant per result | grows with item count, **bounded at 2 observations for per-entry results** | predicate-sized for common cases, list-sized for the tail |
| aggregate results | **constant** (run-scoped applicability, §E.16 — aggregates never carry per-entry evidence) | same — both are constant here | constant |
| multi-observation evidence | carried by the references, not the carrier | same | same |
| negative evidence | needs one absence-predicate per absence fact, **defined in the contract** | expressible inline (`absent-from:run-M`) | defined predicates for the named absences; inline for the rest |
| structural evidence | predicate per structural fact | inline, verbose | mixed |
| contract evolution | **every predicate change is a contract-version change** — visible, but a wrong-edition reader silently mis-reads (the F-TD-10 trap, *detectable* under V2's reject rule but only if the reader checks) | lists evolve freely; old outputs readable forever; contract version only governs grammar | predicate changes versioned; inline lists unversioned — **the two carriers age at different rates** |
| grammar evolution | unaffected | unaffected | unaffected |
| parser complexity | lowest — one token form | low — one list form | **highest — two forms, and a rule for which appears when** |
| testability | contract table is testable as data | per-line, no table | both, plus the selection rule |
| duplication | none | the same field sets re-stated on many lines | none for predicates; lists may repeat |
| future compatibility | strongest for format stability; weakest for self-description | strongest for self-description | splits the difference, at the cost of two mechanisms |

**What makes a versioned predicate stable (M1, as the mandate requires).** Three things, all of
which V2 + G-5 now provide: (i) the predicate's meaning is **fixed by a contract edition that the
output itself names** — the header mark is the predicate's anchor, so a predicate cannot drift
without the version mark moving with it; (ii) predicate definitions are **data, not code paths** —
a table keyed by `(contract-version, predicate-name)` is testable as data and survives
implementation changes, exactly the way `schema_meta` makes the log's shape inspectable; (iii)
evolution is **additive by default**: a new edition may define new predicates and refine old ones,
and §E.29's reject rule means an unknown `(version, name)` pair fails loudly instead of being
guessed. What a versioned predicate does **not** protect against: a reader that ignores the
version mark — P37's falsifier.

**How M2 avoids output explosion in aggregates and multiple observations (M2, as the mandate
requires).** Two structural facts, both already established in this design: (i) **aggregates are
run-scoped** (§E.16) — their applicability is the run, and they never carry per-entry evidence, so
an aggregate's basis line names the run and carries **no field list at all**; the unbounded-growth
scenario never arises; (ii) **per-entry results have bounded evidence** — a mutation result rests
on at most two observations, and its field set is drawn from the fixed observed-field list of
§E.12 (a dozen names at most, in practice three to six). The worst case is a rename line with two
field lists — long, and bounded. Growth is linear in the *number of results the user asked about*,
which is the same growth the output already has; the carrier adds a constant factor per line, not
a new order.

**Assessment.** M5 is **not superior**: it buys M2's self-description only for the tail, keeps
M1's contract dependency for the head, and adds a second carrier plus a selection rule — the
parser complexity of both with the guarantee of neither. It is recorded because the mandate asks,
and it is eliminated on complexity, not on principle. **The choice is between M1 and M2**, and it
reduces to one question: **is a basis line required to be self-describing, or is
self-description-at-a-named-edition sufficient?** That is the same product judgement §E.32
recorded, and it is not this document's to make. **No recommendation is upgraded and none is
withdrawn: M1 and M2 both remain viable, M5 is eliminated, and the decision belongs to the
owner.**

## F. RECOMMENDED DESIGN

The design as it stands after §C–§E. Items marked **DECIDED** are committed
(`UD-016`–`UD-021`); the rest are proposals. **A recommendation is not a decision**, and the
distinction is marked on every line.

1. **A pure skip decision.** `decide(previous, current) -> Skip | Read`, free of syscalls,
   clock and database, testable against hand-built observation sets (§C.1). *Proposal.*
2. **A verified baseline is required.** No skip without a prior `Stable` reading
   (§C.1 condition 2). *Proposal.*
3. **The reading is carried forward, and attributed.** `hash`, `hash_stability` and a new
   `hash_read_run` travel together. `content-verified in run N` becomes the integer
   comparison `hash_read_run == N` (§C.3). **DECIDED — the requirement to distinguish the three
   states is `UD-021`; the schema is NOT decided.**
4. **`basis` is derived, never stored**: `content` / `metadata-match` / `unavailable`,
   computed from `hash_read_run` and the observation's error state. *Proposal.*
5. **For `basis` applicability, use family B1** — emit `basis` on a line that carries its own
   subject, state the rule in the contract, enforce it with a test (§E.4). **RECOMMENDATION,
   NOT a decision.** `UD-019`'s question stays `OPEN`. **F-TD-5 is `RESOLVED AT SEMANTIC LEVEL /
   MECHANISM OPEN`**: B1 addresses applicability, not `UD-017`'s provenance obligation, whose
   semantics J.1 fixed (§E.5) and whose mechanism is open.
6. **`show` names the entry it reports**, so a per-entry value is attributable. Minimum change
   only. **DECIDED — `UD-020`.**
7. **`ctime` is NOT in the skip condition.** The condition of §C.1 is used **without**
   condition 6, which leaves §C.5's false skip reachable and records it as a known limitation
   (`L1`). `ctime` remains a candidate hypothesis under `D-PEND-2` (`OPEN`), neither adopted nor
   eliminated; adopting it requires `E-TD-2` and `E-TD-3` first, neither executed.
   **DECIDED (not to adopt now).**
8. **Verdict preservation is bounded by the evidence each observation holds.** The skip may
   retain a previous content reading, and a mutation preserving the metadata the predicate uses
   may go undetected in that observation. **DECIDED — `UD-021`**, accepted as a known limitation
   (`F-TD-4`), never to be presented as a guarantee.
9. **The existing read guard is untouched.** `observe_content` is not modified; v0.2 changes
   *when it is called*, not what it does. *Proposal.*
10. **`reconcile` keeps its five phases and its rules.** The only change is that a carried hash
    is a legitimate operand for `hashes_equal`/`hashes_differ` — which is what preserves the
    verdicts where the evidence is the same (§C.2). *Proposal.*

What the design deliberately does not do: change the traversal, add a cache outside the log,
add a listing command, resolve `F-V01-1`, redesign `show`, change the path encoding, resolve
`F-V01-8`/`F-V01-9`, touch `material-v1`, or answer `Q25`.

## G. FALSIFIABLE PROPERTIES

Each states a claim, its preconditions, its observable result, and its falsifier. The rule
earned by F-5, F-6 and F-V01-5 is applied: **a test that cannot fail when the property is
removed proves nothing, and is classified as such.**

The mandate's list (P1–P10) was **reviewed, not accepted**. P5 and P8 were reformulated because
as stated they were false; P2 was split because its two halves need different evidence; P10 was
restated because as written it was imprecise; P11–P15 were added. Two properties were found to
be **vacuous** under the design as adopted, and are labelled so rather than kept as decoration.

### G.1 The four kinds, kept apart

Every property below is tagged with what kind of guarantee it is. Conflating these is how a
limitation becomes a false guarantee.

| Kind | Meaning | Where it comes from |
|---|---|---|
| **ALGO** | Guaranteed by the algorithm, for any inputs | Testable against hand-built observation sets; no filesystem needed |
| **FS** | Guaranteed only because the filesystem/platform behaves a certain way | Testable only where that behaviour can be provoked; must be declared where it cannot |
| **UNKNOWN** | Not established by any evidence this project holds | Cannot be a property of v0.2; it is a question |
| **LIMITATION** | Known, reachable, and **not** prevented | Stated as a limitation; **never** written as a property that passes |

**Overlap, recorded so tests are not double-counted.** P27–P29 sharpen P18/P23 for the item kinds
§E.12 introduced; P30 is P25 extended to the line terminator; P31 sharpens P20's "resolves"; P32 is
P17's precondition made explicit; P33 is the negative form of P17 and P18 — it forbids a
*solution* rather than requiring a behaviour. None of them replaces the others: P18 asks whether the
values are recoverable, P27 asks whether *two* observations are; P25 asks whether the line parses,
P30 whether the line *exists*.

**On the mandate's P-TD-B as originally phrased.** "The evidence that produced that result is
reconstructible **to the degree required by `UD-017`**" was **not conserved**, because at the time
its precondition was insufficient: `UD-017`'s degree was exactly what was ambiguous (E.5), so the
property had no defined threshold and **could not fail**.

**J.1 now defines the threshold** — *locatable in the durable record* (§E.5) — so the obligation is
conserved as **two checkable halves**: **P17** (the observation(s) and the field set are
recoverable) and **P18** (the values are recoverable from the durable record). Neither is vacuous,
and together they are what "reconstructible to the required degree" now means concretely. The
original phrasing is recorded rather than quietly replaced, because a property with an undefined
threshold is the same class of defect as a test that cannot bite, and it is worth seeing how the
decision repaired it.

**P-TD-C is conserved but not duplicated** (see its row). **P-TD-A is conserved with its scope
narrowed** — as written it was ambiguous for aggregates, where the subject is a run and not an
entry.

|---|---|---|---|---|---|
| **P40** | **The escape itself round-trips**: a value consisting of the escape character — alone, doubled, trailing, and adjacent to every domain byte — survives `parse(serialize(V)) == V` | The escape character is `\` today; the property is stated for whatever the exact specification chooses | Identity holds in every position | Any position where the escape collapses two preimages into one rendering (injectivity broken) — the classic failure of an escape that does not escape itself | **ALGO** |
| **P41** | **Delimiter and terminator round-trip**: a value containing the field delimiter, the item delimiter, and the result boundary — in any run length and any combination — survives the parse with identity and associations intact | G-1's coverage obligation (§E.27): the escape covers **every** delimiter and the line terminator | The parsed value equals the original; the result count is unchanged | Any delimiter byte that survives serialization raw — today's F-TD-9/F-TD-11 state: two spaces and `0x0A` pass through unescaped | **ALGO** |
| **P42** | **Invalid escape sequences are rejected, not guessed**: a dangling `\x`, an unknown escape name, or a truncated hex pair yields a parse error naming the position | Input that is syntactically invalid under G-1 + G-5 — malformed input is the *only* place a falsifier may be malformed | Rejection with position | Any code path that decodes anyway, emits the sequence literally and continues, or resynchronizes — the prohibitions §E.29 fixed | **ALGO** |

**Relationship to the earlier properties, stated so coverage is not double-counted.** P40–P42 are
P34 (identity), P35 (associations) and P36 (fail-closed) *made checkable for G-1 specifically*;
P41 additionally carries P30's boundary obligation into the family. The arbitrary-byte and
combination round-trips the mandate lists are P34's domain, unchanged — P40/P41 name the
G-1-specific *mechanisms* (the escape character, the delimiters) through which P34's domain cases
fail in practice.

### G.2e Update to the audit — verdict-equivalence check on the new properties

P34–P39 were audited like the rest (§G.5), and **P40–P42 with them**. **None implies verdict
equivalence**: they constrain
how results are written and read, never which verdict is produced. P38 comes closest to touching
behaviour and does not: a re-flow that changed a *verdict* would fail P35 first, as an association

### G.3 The enumerated verdict divergence (F-TD-4)

P14 is only meaningful if the exception is named. It is, and it is a **real, reachable
divergence** — found while reviewing these properties, not assumed away.

**Scenario.** Run 1 records bytes `B1`. Between runs 1 and 2 a writer replaces the bytes with
`B2`, **same size, mtime restored**. Between runs 2 and 3 the file is `touch`ed (mtime moves,
bytes still `B2`).

| | run 2 | run 3 | verdict at run 3 |
|---|---|---|---|
| **v0.1** | reads → `H(B2)`; metadata equal → `Unchanged` | reads → `H(B2)`; mtime moved, hashes equal → **`Unchanged`** | `Unchanged` |
| **v0.2** | **skips** → carries `H(B1)`; `Unchanged` | no skip → reads `H(B2)`; mtime moved, `H(B1) != H(B2)` → **`Modified`** | `Modified` |

Both are defensible readings of the evidence each implementation actually holds: v0.1's run 2
absorbed the change by reading; v0.2's run 2 did not, so the change surfaces one run later.
Neither is "wrong" — but they are **not the same verdict**, and the objective says verdicts are
preserved.

**This is the honest cost of the skip, and it belongs in the version record as a known
limitation, not hidden in a test exception.** It also shows why P14 cannot be written as
"verdicts are identical": that statement is false, and a test asserting it would either fail or
have to be weakened silently.

The class is: *a content change that does not move metadata, occurring during a run that one
implementation read and the other skipped.* It is reachable in both directions (a change and
revert can produce the mirror image). The design does not eliminate it; `hash_read_run` makes
it *visible* — a reader can see that a run's reading is old — which is the most the design can
do without reading everything.

**Status: ACCEPTED, as a recorded commitment (`UD-021`, 2026-09-13).** The owner accepted this as
a known and reachable limitation of the skip mechanism, without reconsidering v0.2's objective
and without removing the skip. It is therefore:

- **not** an unresolved question;
- **not** a test exception to be papered over;
- **not** a guarantee of v0.2, and never to be presented as one;
- documented in `UD-021`, in `V0.2-SCOPE-PROPOSAL.md` §3, and in the version record when v0.2
  closes.

What `UD-021` also fixes is the vocabulary: **verdict equivalence**, **reuse of prior evidence**,
**content verification** and **metadata-stable** are four distinct things and must not be
conflated. In this scenario v0.2's run 3 *did* verify content (it read the bytes); what it could
not do was reproduce the verdict that a re-read at run 2 would have produced. Those are different
failures and the record keeps them apart.

### G.4 Known limitations carried by this design

Stated here so they are not mistaken for properties. **None of these is a guarantee.**

| # | Limitation | Why it is reachable |
|---|---|---|
| **L1** | **Inode reuse with matching metadata produces a false `Unchanged`** | §C.5. `ctime` is not adopted, so nothing in the condition detects it. `FS`-dependent and `UNKNOWN` in frequency — v0.1 observed reuse on the ext4 CI runner, never on tmpfs/btrfs |
| **L2** | A content change that does not move size or mtime leaves no trace in a skipped run | §C.6, F-TD-3. The verdict is `Unchanged` in both implementations; what v0.2 loses is the **recorded evidence** |
| **L3** | A change-and-revert between two runs is invisible | Inherent to sampling |
| **L4** | The verdict divergence of G.3 | F-TD-4. **Accepted as a limitation by `UD-021`** — documented, not unresolved, and never a guarantee |
| **L5** | A filesystem that does not generate its own timestamps | Irrelevant while `ctime` is unused; becomes relevant if it is adopted (`UNKNOWN`, D-F) |

L1 is the one that must never be restated as a property. The property that *can* be asserted is
the conditional P8, and only once `ctime` is adopted — which it is not.

### G.5 Audit — does any property still imply verdict equivalence?

`F-TD-4` falsified the claim that v0.2's verdicts always equal what a full re-read would produce.
Every property was therefore re-read for a verdict-equivalence implication. **Result: none
remains, and three needed explicit repair.**

| # | Verdict-equivalence implication? | Action taken |

## H. EXPERIMENTS

Designed to be able to **contradict** the design. None is a confirmation exercise.

**Execution status: NONE of these has been executed.** `E-TD-2`, `E-TD-3` and `E-TD-11` are
**pre-registered** below — the protocol is fixed *before* the run, which is the rule
`DOCUMENTATION-ARCHITECTURE.md` §10 rule 3b states and which `EXP-CTIME` did not follow. They
are not executed because each requires code (a probe that writes, restores metadata and observes
between states; or a built v0.2 output to transform), and implementation is not authorized.

**Separation from historical evidence.** `EXP-CTIME` remains the historical record it is, with
its provenance caveat intact. A new run is a **new experiment with a new ID**; its results are
not evidence for the old question retroactively, and re-running the same script does not
convert one observation into a replicated one. Where `E-TD-2` re-uses `EXP-CTIME`'s cases, it
says so and reports them as re-measurement, not as confirmation.

### H.1 E-TD-2 — the metadata-restoring writer (PRE-REGISTERED)

**Question.** Does the skip condition of §C.1 detect a content change that leaves size, mtime
and physical identity equal — and does adding a `ctime` term change the answer?

**Hypotheses, stated so they can fail:**

| # | Hypothesis | Falsified by |
|---|---|---|
| **H2-a** | Without `ctime`, a writer that restores size and exact mtime produces **no detectable difference** at the observation surface | Any case where the observation differs |
| **H2-b** | With `ctime`, that same case **is** detected | Any case where the bytes differ, size/mtime/`dev`/`ino` are equal, and `ctime` is **also** equal |
| **H2-c** | Adding `ctime` never *enlarges* the skipped set | Any input where the `ctime` condition skips and the metadata-only condition does not |
| **H2-d** | The two implementations' `changes` verdicts agree on this case | A verdict difference |

**Filesystems.** tmpfs and btrfs (available locally) **and ext4** — ext4 is the one that matters
and the one this project cannot probe locally. It must be probed in CI or on a machine with
ext4; if neither is available at execution time, the ext4 arm is recorded as **NOT EXECUTED**
and the result is reported as partial. It is not silently dropped.

**Procedure, fixed in advance:**

1. Create a temp directory on the filesystem under test. Record kernel, filesystem type and
   mount options.
2. Write `f` with `B1` (known bytes, length `L`). Record `stat`: size, mtime, `ctime`, `dev`,
   `ino`.
3. Observe with the metadata-only condition. Record the decision (`Skip`/`Read`) and, if read,
   the hash `H1`.
4. Sleep past the timestamp granularity of the filesystem (start at 1 s; record the granularity
   assumed).
5. Write `B2` (`B2 != B1`, **same length `L`**) and restore mtime to the recorded value via
   `utimensat`. Do **not** attempt to restore `ctime` — it is not settable, and the attempt is
   itself a case.
6. Record `stat` again. Assert that size, mtime, `dev` and `ino` are equal to step 2. If any is
   not, the case is **invalid** and is recorded as such — not as a result.
7. Observe again, under **both** conditions: (i) metadata-only, (ii) metadata + `ctime`.
   Record each decision.
8. If a `Read` happened, compare `H2` against `H1`.
9. Repeat steps 1–8 with three variants: **atomic replacement** (`rename` over the target),
   **`touch` only** (mtime moves, bytes equal), and **`chmod` only** (no content change).
   These are controls: the second and third must force a re-read and must not report a content
   change.
10. Run the whole sequence ≥ 20 times per filesystem per variant, and report the distribution,
    not a single sample.

**What falsifies what:**

- **H2-b dies** if a single case has bytes differing, size/mtime/`dev`/`ino` equal, and `ctime`
  equal. One instance is enough; this is the load-bearing falsifier for adopting `ctime`.
- **H2-c dies** if any case skips under `ctime` and not under metadata-only. This arm does not
  need a filesystem at all and should be run as a property test over hand-built inputs, where
  it is exhaustive rather than sampled.
- **H2-d dies** on any verdict difference; if it dies, the case joins G.3's enumerated class.

**What this experiment cannot establish.** That `ctime` *always* moves — no finite sample can.
The hypothesis is stated as a search for a counterexample (H2-b), which is the only form the
evidence can support.

**Anti-confirmation measures, because the author wants `ctime` to work:**

- The protocol above is fixed before the run and is not edited afterwards.
- Steps 9's controls are cases where `ctime` *causes extra work*; reporting them is mandatory.
- The falsifier for H2-b is a single counterexample, and finding one is a **result**, not a
  failed run.
- The ext4 arm is the one that matters, and its absence is reported, not omitted.

### H.2 E-TD-3 — inode reuse with matching metadata (PRE-REGISTERED)

**Question.** Does a delete-and-recreate at the same path, with matching size and mtime,
actually receive the same `dev`+`ino` — and if so, does the skip condition produce a false
`Unchanged`?

**Priority: ext4.** v0.1 records that inode reuse *was observed* on the ext4 CI runner
(`docs/versions/v0.1.md`, limitation 9) and *was not* on tmpfs or btrfs. So ext4 is where the
scenario is known to occur, and a local-only run cannot answer the question. If ext4 is
unavailable at execution time, the experiment is recorded as **NOT EXECUTED on the filesystem
that matters**, and the local arms are reported as a weaker result.

**Procedure, fixed in advance:**

1. On the filesystem under test, create `p` with known bytes; record `dev`, `ino`.
2. Delete `p`.
3. Create `p` again with **different** bytes of the **same length**; restore mtime to the
   original value.
4. Record `dev`, `ino`, size, mtime, `ctime`.
5. Repeat until the pair (`dev`, `ino`) is **reused**, or a pre-declared budget of attempts is
   exhausted.
6. **Record which happened.** The two outcomes are both results and are reported differently:
   - **Reuse observed** → the scenario is real, and step 7 runs.
   - **Budget exhausted without reuse** → the scenario was **not provoked**. This is recorded as
     "not provoked", **never** as "does not occur" — the v0.1 discipline, and the F-6 rule.
7. With the reused pair, run the skip condition. Record the decision.
8. Run the `changes` comparison across the two observations and record the verdict.

**What falsifies what, and what is only demonstrated:**

- **Demonstrating a LIMITATION.** If reuse occurs (step 5) and the condition produces a skip
  (step 7), then L1 is **demonstrated** — a false `Unchanged` for different content. This is
  evidence *against* the design's safety, and it is the result the experiment is looking for.
- **NOT demonstrating a guarantee.** A run where reuse does **not** occur, or where reuse occurs
  and no skip happens, does **not** show that the false skip is impossible. It shows it was not
  provoked in that run. **This is the distinction the mandate requires and the one easiest to
  get wrong:** the experiment can demonstrate a limitation and can never demonstrate the
  absence of one.
- **P8 is not tested by a negative result.** P8 is conditional on `ctime`, which is not adopted;
  it is exercised by `E-TD-2`, not here.

**Anti-confirmation measures:**

- The failure to provoke is pre-declared as a possible and legitimate outcome, with its own
  reporting language.
- The experiment is not run "until it reproduces"; the budget is declared before the run.
- A result of "not provoked locally, not executed on ext4" is a **complete and honest** outcome
  and requires no further work to be reportable.

### H.3 E-TD-11 — the F-TD-5 ambiguity experiment (PRE-REGISTERED)

**Question.** Under the semantics J.1 fixed — *a result must provide a reference sufficient to
locate, in the durable record, the evidence that produced it* — can a reader reconstruct, for each
result, (i) which entry it applies to, and (ii) **which observation(s) and field set** its evidence
consists of, and can the reference then be **resolved against the durable record** to obtain the
values?

**This revision is not cosmetic.** The first version of this protocol gave the reader the output
**only — "not the log, not the source"** — which tests interpretation **(a)**, the reading J.1
**rejected**. Under (b) the values are expected to come from the durable record; withholding it
would have measured a property the contract does not claim, and a failure would have been reported
as a defect of the design. The protocol now tests the decided semantics, in its two steps.

**What it is trying to do: demonstrate that the design is ambiguous.** This is the purpose, and it
is stated as such so that a negative result is not mistaken for a failed experiment.

**Hypotheses, stated so they can fail:**

| # | Hypothesis | Falsified by |
|---|---|---|
| **H11-a** | Applicability (A) survives every transformation in the list below | Any transformation after which a result's subject is not determinable |
| **H11-b** | **Step 1** — from the output plus the contract, the observation(s) and field set are recoverable for every result | Any result whose evidence cannot be narrowed to (observation, field) items |
| **H11-c** | **Step 2** — the reference resolves against the durable record, and the values obtained match what the result asserts | A reference that does not resolve, resolves to more than one observation, or yields values inconsistent with the result |
| **H11-d** | A carried reading after a rename is **locatable** | A reader who cannot identify the observation that produced the carried hash — **the F-TD-6 falsifier** |
| **H11-e** | A cross-entry reference is **locatable** | A reader who cannot reach the referenced entry's observation — **the F-TD-7 falsifier** |
| **H11-f** | The output parses unambiguously under the stated grammar, **and every value survives the parse with its identity intact** | A permitted output whose parse yields a wrong field set — **the F-TD-9 falsifier**; or a **valid** value that does not survive the parse — **the F-TD-11 falsifier**; or a round-trip that loses a control character, a whitespace run, or a byte |
| **H11-g** | The **four run roles** are distinguishable | A reader who cannot tell a `metadata-stable` result re-observed in run N from one whose bytes were read in N — **the F-TD-8 falsifier** |

**Fixture — built to contain the hard cases, not a convenient one:**

| Element | Why |
|---|---|
| `a.txt` changed between runs | a content-verified result (`basis=content`) |
| `b.txt` untouched | a `metadata-stable` result whose reading is older than its run — H11-g's case |
| `c.txt` renamed to `d.txt` | a carried reading whose observation is at **another path** (F-TD-6) |
| two hard links, one entry deleted | a cross-entry reference (F-TD-7) |
| a path containing **two consecutive spaces** | the delimiter case (F-TD-9) |
| a path containing a **line terminator** | the boundary case (F-TD-11) — today it splits the result in two |
| a path combining a **backslash and a newline** | a **combination** case — today the backslash is escaped and the newline is not, the exact class P34 warns single-case testing misses |
| a path containing a **carriage return** | the CR case — same escape coverage obligation as newline, distinct byte (P41's domain) |
| a path containing a **tab** | control character outside the line-structure pair — P34's domain |
| a path containing **non-UTF-8 bytes** | the existing `\xNN` mechanism — P34 must hold with it *and* under the new value-level escape |
| a path containing the **delimiter bytes** plus a **backslash** | the G-1 combination P40/P41 exist to catch: the escaped delimiter's backslash followed by the escape character |
| a run with an unobservable path | a run-level fact (`complete=false`) |
| three runs | so that "older than its run" is representable |

**Transformations, applied in order, each recorded separately:**

1. **Reordering** — permute the output lines.
2. **Subject removal** — delete the subject field from every line.
3. **Re-flow** — wrap every line at a fixed width.
4. **Delimiter split** — split every line on the delimiter the grammar states and re-emit the
   tokens.
5. **Serialization round-trip** — convert to a structured form and back.
6. **Position change** — move the reference to the end of the line.

**Two-step task given to the reader** (`AI-INDEPENDENT` per `UD-015`; the owner delivers it, Hermes
does not contact or select a participant):

1. **Given the output and the stated contract** — for each result: which entry or object it applies
   to, and which observation(s) and field set its evidence consists of. **The durable record is not
   provided for this step**, because (b) does not require the output alone to yield the values.
2. **Given the durable record** — resolve each reference and state the values. **The values are
   expected to come from here**; a reader who cannot reach them at this step is the failure the
   semantics forbids.

Reporting step 1 and step 2 separately is mandatory: a step-1 failure is a defect of the output's
contract, and a step-2 failure is a defect of the reference.

**What falsifies what — and the four defect classes it must separate.** The mandate requires the
protocol to distinguish *which kind* of defect a failure is, because the four have different
consequences and different owners. A failure is reported under exactly one class:

| Class | What failed | Falsifiers | Consequence |
|---|---|---|---|
| **D1 — applicability** | the result's subject is not determinable | H11-a | the output contract is wrong; a `UD-020`/B1 failure |
| **D2 — provenance** | the grammar parses, but the evidence cannot be narrowed to (observation, field) items, or the reference does not resolve | H11-b, H11-c, H11-d, H11-e | the mechanism is wrong; F-TD-6/F-TD-7 |
| **D3 — grammar** | the parse itself fails: **destruction of a value boundary**; **an ambiguous parse** (more than one derivation); **loss of a control character, whitespace run or byte** in round-trip; **loss of an association** | H11-f | the grammar is wrong; F-TD-9/F-TD-11; P34/P35/P36 |
| **D4 — durable reconstruction** | the reference resolves but the record cannot reproduce the values, or the four run roles cannot be separated | H11-g, and step 2 of H11-c | the *record* is wrong, not the output — a schema/persistence failure |

**D3's sub-classes are stated because they have different fixes.** Boundary destruction is fixed by
the delimiter scheme; ambiguity by the escape/framing definition; byte loss by the escape function's
coverage; association loss by the contract's declaration of the semantic unit. A D3 failure
reported only as "does not parse" would not say which layer to change — the same mis-direction risk
the D1/D4 separation guards against. **The D2 row's precondition is also now explicit**: a grammar
failure can *mask* a provenance failure (an unparseable output proves nothing about the reference),
so D3 takes precedence when both are present — a failure that appears to be D2 and D3 is reported
as D3.

**Why the classes must be separated.** A D1 failure is fixed by changing the output's subject
convention; a D4 failure is fixed by changing what is persisted, and **no change to the output would
fix it**. Reporting them as one "the reader could not reconstruct the evidence" would send the fix to
the wrong place — which is the same error EXP-AI-01's Q2 recorded, where a material defect was
nearly read as a participant disagreement.

**One line per failure, and no line may be counted twice.** A failure that appears to be both D1 and
D2 is reported as D1, because a reference cannot be resolved against a subject that was never
established.

**Fixture addition (F-TD-11).** The fixture gains **a path containing a line terminator**, in addition
to the two-space path. It is the only element that can falsify H11-f through D3 while every other
hypothesis passes, and without it F-TD-11 is untested — as it is today, since no test in the suite
covers a control character in a name.

**Hypotheses H11-a..H11-g are unchanged** and each maps to exactly one class above. **The two-step
structure is unchanged**: step 1 (output + contract) can only produce D1, D2 or D3; step 2 (record)
can only produce D4. That asymmetry is what makes the classes separable at all, and it is the reason
the protocol was revised after J.1.

**Anti-confirmation measures.** The experiment is designed to *find* ambiguity, so the risk is the
opposite of E-TD-2/E-TD-3: the risk is manufacturing ambiguity by withholding context. Three
guards. First, **each step is given exactly what the semantics says it may rely on** — the contract
at step 1, the record at step 2 — so "the contract does not say" is distinguishable from "the
output does not determine", and neither is confused with "the values are not in the record".
Second, each transformation is reported separately, so a failure under re-flow is not reported as a
failure of applicability. Third, **"no ambiguity found in this configuration" is a legitimate,
complete result** and requires no further work to be reportable.

**What this experiment cannot establish.** That the design is unambiguous *in general* — it tests
one fixture and one reader. And it establishes nothing about A1: per `UD-015` it can surface
defects and unblock a decision, and can never satisfy the human-independent requirement.

**Step 2 — metadata fields.** `identity::ctime_of()` (Unix: `ctime`/`ctime_nsec`; non-Unix:
`None`). `Entry.ctime: Option<(i64, u32)>`. `ObservedPath.ctime`. **Recorded but not used in
the condition** — `ctime` is not adopted (§F.7). It is captured so that adopting it later does
not require a second schema change; the field's presence is not a claim about its use.
*Files:* `umbral/src/identity.rs`, `umbral/src/scan.rs`, `umbral/src/reconcile.rs`.

**Step 3 — persistence.** `Observation` gains `ctime` and `hash_read_run`. Schema version
→ `umbral-v0.2`, with two new nullable columns and the existing `CHECK` retained. **v0.1
logs: migrate, do not refuse.** Every v0.1 row was read in its own run, so
`hash_read_run = run_id` is not a guess — it is what v0.1's behaviour guarantees. Refusing
the log would discard history, which the objective forbids.
*Files:* `umbral/src/log/mod.rs`, `umbral/src/log/sqlite.rs`.

**This step is a PLAN, not a decided schema.** What is committed (`UD-021`) is the requirement
that the three states of §C.3 be distinguishable in the reconstruction. The column set, the type
of the attribution, whether `hash_read_run` is the right shape for it, and the migration policy
are all **open** (§J). A later design step may satisfy the requirement differently and this plan
would then be wrong, not violated.

**Step 4 — `observe` consults the previous run.** Load the latest run's observations into a
by-path index (new `O(corpus)` cost, §B.1 item 2), decide per entry, read only where the
condition fails, carry the reading forward where it does not. The condition is §C.1 **without**
condition 6.
*Files:* `umbral/src/main.rs`.

**Step 5 — `basis` in the output.** Derived from `hash_read_run` and the error state.
`status` and `observe` gain a per-basis breakdown on a run-scoped line; `changes` mutation
lines gain `basis=` beside the existing `path=`. **`show` gains a field naming the entry it
reports**, per `UD-020` — the minimum that makes a per-entry `basis` attributable. No redesign
of `show`, no new command, no resolution of `F-V01-8`/`F-V01-9`, and no change to the
path-encoding note.
*Files:* `umbral/src/report.rs`.

**Step 6 — `check` verifies the new invariant.** Every row with `hash_read_run < run_id`
must be justified by an earlier observation of the same path with that run id and the same
hash.
*Files:* `umbral/src/report.rs`.

**Step 7 — tests.** Unit (the pure decision, P8/P12/P15); contractual (P1, P2, P3, P11);
falsification harness extended with a metadata-restoring op (P14, P5, P9); counters (P10);
regression (the 101 existing tests, unchanged, on tmpfs/btrfs/ext4).
*Files:* `umbral/tests/` — new `incremental.rs`, `basis_contract.rs`; extensions to
`fs_matrix.rs`, `harness_falsification.rs`, `output_contract.rs`.

**Step 8 — reader protocol.** The A2-8 legibility question and the A1-AI/A1 tracks, per
`UD-015`. Not a code step.

**Documentation that must change with the code** (the doc-sync policy, §K).

**Obligations from F-TD-5 that this plan does not yet carry, recorded so they are not lost.**
Steps 3, 5 and 6 below were written before §E.5–E.11 and do not reflect them. Specifically: step 3's
persistence must satisfy **F-TD-6** (an observation reference must distinguish `(run_id, path)`, not
a run), step 5's output must satisfy **F-TD-7** (cross-entry evidence must be locatable) and
**F-TD-9** (the grammar must be unambiguous for permitted values), and step 6's `check` must satisfy
**F-TD-8** (the state of knowledge at run N is recomputable from rows ≤ N, with the four run roles
distinct). **The plan is deliberately not rewritten**: rewriting it would imply those mechanism
questions are settled, and they are open (§J.1–J.9). Whoever writes the implementation plan proper
takes them as inputs.
