DOCUMENTATION ARCHITECTURE AUDIT
================================================================================
Added 2026-09-10 as a required section of this audit. Design output lives in
DOCUMENTATION-ARCHITECTURE.md; its evidence base lives in
research/DOC-ARCHITECTURE-RESEARCH.md (DR-1..DR-11).

1. WHAT IS CURRENTLY GOOD
- The flat, topic-per-file structure was already minimal and survived this audit
  unchanged. No folder was added, no file was renamed, no numbering scheme introduced.
- Every file has one subject and one audience; the map and read order existed.
- IDs (A-n, C-n, R-n, J-n, H-n, Q-n, T-n, UD-n, S-n, MC §n) already made the repository
  addressable, which is the property that makes context economy possible later.
- Sources and statuses were already recorded per claim, which is what made the MC
  recovery a surgical update instead of a rewrite.
- Nothing depends on Hermes or on any tool: plain Markdown, plain folders.

2. WHAT IS CURRENTLY WEAK
- No single place stated the authority ladder. It was implicit and had to be inferred
  from prose — the exact confusion the project exists to prevent.
- Status lines existed only as "Status: ..." inside prose, and were absent on several
  files (README, PRINCIPLES, CONSTRAINTS, INGEST-NOTES).
- Stale statements survived a change that invalidated them: README still claimed "no
  DECISIONS.md" and "no decision exists yet" after decisions existed.
- Two audiences were mixed in one file: product decision principles and documentation
  principles shared PRINCIPLES.md.
- No routing rule existed, so the answer to "where does this go?" was a judgement call
  every time — the mechanism by which repositories sprawl.
- No historical convention: frozen artifacts and living documents were indistinguishable.
- The research chain (source -> claim -> interpretation -> hypothesis -> experiment ->
  decision) existed in the charter and in practice, but had no documentary form.
- No entry point for AI agents, despite this being an AI-native project.
- No version history: the repository was not under version control, so the only record
  of change was prose inside files.

3. WHAT IS DUPLICATED
- The tension list appeared in both INGEST-NOTES §4 and OPEN-QUESTIONS.md. Resolved:
  canonical is T1-T6 in ARCHITECTURE-HYPOTHESES.md / OPEN-QUESTIONS.md; INGEST-NOTES
  keeps its copy as frozen ingestion history with a supersession note.
- Documentation principles were duplicated in intent between PRINCIPLES.md and the
  bootstrap's epistemic contract. Resolved: DP-1..DP-10 in
  DOCUMENTATION-ARCHITECTURE.md; PRINCIPLES.md now maps to them and covers product
  heuristics only.
- AGENTS.md and README.md share the authority ladder by design (one is a pointer).
  Accepted duplication of ~5 lines; monitored in DQ-1.
- No duplicated facts were found among canonical documents.

4. WHAT IS MISSING
- Authority ladder at entry: now in README and AGENTS.md.
- Routing rule for new information: now DOCUMENTATION-ARCHITECTURE.md §10.
- Lifecycle definition (living vs frozen): now §4.
- Research/experiment chain with homes per step: now §8.
- Historical convention (supersession lines, dated records): now §7.
- Context-economy model: now §9.

5. WHAT DOCUMENTATION RESEARCH EXISTS
Eleven sources, assessed in research/DOC-ARCHITECTURE-RESEARCH.md with explicit
verification markers: Nygard/ADR community/MADR/Fowler on decision records; Diátaxis on
organizing by reader need; ISO/IEC/IEEE 42010 on concerns, viewpoints and rationale;
arc42 on "every kind of information has a place"; Pirolli & Card on information
foraging and information scent; Anthropic's context-engineering guidance on the
smallest high-signal token set; AGENTS.md (adopted convention) versus llms.txt
(proposed, minimal adoption); lab-notebook and data-provenance practice; OASIS DITA on
topic-based reuse; and documentation-drift tooling (Vale, docs-health, staledocs).
Limitation recorded: the extraction backend was search-only, so several sources were
assessed at snippet level and are marked as such.

6. WHAT THE RESEARCH ACTUALLY SUPPORTS
Supported and adopted: one decision per immutable record with supersession (DR-1);
organize by reader need, not by artifact origin (DR-2); rationale travels with the
claim (DR-3); one home per kind of information (DR-4); authority visible at entry
(DR-5); smallest sufficient context (DR-6); a thin agent entry point, and the standard
that a convention earns its place by being used (DR-7); dated immutable records
(DR-8); reuse by reference (DR-9); deterministic drift indicators, not prose linting
(DR-10).
NOT supported by evidence, therefore not adopted: epistemic-state metadata as a
documentation feature (no evidence it improves comprehension); agent-specific content
duplication; any documentation tooling at this scale; and — importantly — there is no
standard for "project memory serving a human and an AI simultaneously". FSP's
documentation architecture is a synthesis, not an application of best practice, and is
therefore treated as an experiment (§14).

7. WHICH CURRENT FSP DOCUMENTATION ASSUMPTIONS ARE WEAK
- "Documentation minimalism" was asserted without a routing rule to enforce it; it is
  now testable rather than aspirational.
- The claim that one file per topic is right at this scale is unvalidated — it is a
  reasonable default, and EXP-DOC-1 is the test.
- The assumption that a status line suffices to prevent authority confusion is
  untested; the navigation test measures exactly this.
- The assumption that OPEN-QUESTIONS can carry dated update blocks indefinitely is
  already strained (two blocks in one file); consolidation trigger defined in §12 M2.
- The assumption that the repository can be both a laboratory and a memory without
  contaminating the product's architecture is a risk, not a fact (§0 X1/X2).
